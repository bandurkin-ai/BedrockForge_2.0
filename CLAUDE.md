# BedrockForge 2 — правила для Claude

## Проект
Desktop-ГГИС для Windows 11: Electron (app/) + React/TS/three.js (ui/) + Python 3.12
ядро bf-core (core/) + SQLite/Parquet/DuckDB. Офлайн. Интерфейс только на русском.
ТЗ: docs/spec/00-index.md (этап → файлы). Решения: docs/adr/. Состояние: PROGRESS.md.
Справочник BF (только чтение, через explorer): ветка `claude/laughing-bohr-gpy965`
(`git worktree add /home/user/bf-ref origin/claude/laughing-bohr-gpy965 --detach`).

## Команды
- Ядро: `cd core && uv sync && uv run pytest -q -x --tb=short`
- Ядро, линт: `uv run ruff check . && uv run mypy bf_core`
- Ядро, БД на PostgreSQL: `BF_TEST_PG=postgresql+pg8000://… uv run pytest -q -m db` (драйвер pg8000 — BSD, ADR 0003)
- Ядро, самопроверка зависимостей: `uv run python -m bf_core --selftest`
- Интерфейс и оболочка (npm workspaces ui, app): `npm ci && npm test -- --reporter=dot && npm run typecheck`
- Сборка интерфейса и оболочки: `npm run build`
- E2E (Linux, программный WebGL): `cd app && xvfb-run -a npx playwright test`
- Замеры: `uv run --project core python -m bench.run --profile ci --check`
- Сборка bf-core: `cd core && uv sync --group build && uv run pyinstaller bf-core.spec`
- Сборка .exe — только в CI windows.yml (сборка + дымовой E2E, артефакт .exe не выгружается; выпуск — release.yml)
- ТЗ → spec: `pandoc docs/TZ/BF2-TZ.docx -t gfm --wrap=none -o /tmp/tz.md && python3 tools/spec/split_tz.py /tmp/tz.md docs/spec`
- В облаке uv: `export UV_SYSTEM_CERTS=1; unset UV_NATIVE_TLS` (прокси с собственным CA); uv 0.13.6 (`pip install --user uv==0.13.6`)
- Версии: только по ADR 0001 (точные `==`, `exclude-newer`, `npm install --before=<дата>`); новая зависимость — через ADR

## Структура
app/ оболочка (src/main, src/preload, static/ заставка, e2e/) · ui/src/{shell,viz,charts,edit,modules/<модуль>}
· core/bf_core/<модуль> (api — FastAPI; роутер `<модуль>/router.py` регистрируется в `api/modules.py`)
· core/tests · bench/ (run.py, budgets.json, scenarios/) · tools/ (gen/, ci/, spec/, bf-license — Э24)
· docs/{spec,adr,USER_GUIDE.md,CHECKLIST.md} · tests/data/real/ (файлы real_data, только чтение)

## Модели (решение заказчика 2026-11-23; основная сессия — Sonnet 5.5)
| Модель | Назначение | Не поручать |
|---|---|---|
| Haiku 5.5 | поиск по коду, переименование, шаблоны, простые тесты, правки по готовому списку, запуск тестов и разбор логов (explorer, test-runner, ci-triager) | проектирование, сложная логика импорта и обработки данных, ошибки без понятной причины |
| Sonnet 5.5 | основная разработка: модули, UI, импорт, тесты, рефакторинг внутри модуля; kernel-engineer, reviewer этапа, docs-writer; разбор падений | схема данных, интерфейсы между модулями |
| Opus 5.5 | architect, ADR, схема данных, интерфейсы между модулями, планирование блока при изменении ядра, баги, не решённые со второй попытки Sonnet; сложные вычислительные ядра при неудаче Sonnet | рутинные правки |
| Fable 5.2 | только один раз в конце вехи, после полной реализации и тестов: ошибки, расхождения с ТЗ, проблемы с данными, краевые случаи; минимальные правки; безопасность Э24–Э25 — тоже в конце своей вехи | разработка, новый код, архитектурные решения |
- Каждой подзадаче — самая лёгкая подходящая модель; модель субагенту передавать явно.
- Эскалация: Haiku → Sonnet (не решено с первой попытки или тесты падают); Sonnet → Opus (архитектура или вторая попытка без результата). Без причины не эскалировать. Механику после Sonnet/Opus — на Haiku.
- Fable получает: diff вехи, текст ТЗ вехи, результаты тестов. Архитектурные проблемы не переписывает — фиксирует в отчёте. Нужна новая функция или изменение ТЗ — остановить блок, письмо заказчику, не выполнять.
- Порядок вехи: планирование (Opus при изменении схемы данных или ядра, иначе Sonnet) → реализация (Sonnet, механика Haiku) → тесты (Haiku запускает, Sonnet разбирает) → проверка Fable → отчёт.
- Отчёт на согласование (без вступлений): «Выполнено» (пункт ТЗ — статус) · «Модели» (подзадача | модель | причина выбора или эскалации) · «Проверка Fable» (файл | проблема | исправление | статус) · «Не решено и вынесено на решение» · «Тесты» (пройдено / упало, известные падения).
- Лимит субагентов (указание заказчика 2026-11-23): read-only и механические (Haiku) — до 6 одновременно; пишущие код (worktree) — до 5, по необходимости. Режим расхода — в PROGRESS.md (таблица 13.4 ТЗ).
Агенты волны, которые правят код, — с `isolation: "worktree"` (своё дерево и ветка); оркестратор сливает их ветки
`git merge --no-ff` при приёмке. Бриф — навык `/wave-brief`. Навык `/pr-precheck` отключён (указание заказчика 2026-11-25).
Хуки (`.claude/hooks/`): запрет `git stash`, `git add -A/.`, `rebase`, `push --force` и push одних `*.md` в открытый PR;
запрет правки `tests/data/real/**` и lock-файлов; после правки — ruff по файлу и предупреждение о > 600 строках.

## Чекпойнт (после каждого подшага 30–45 мин)
тесты → коммит «Э<N>: …» / «wip(Э<N>): …» → PROGRESS.md «Сейчас» и «Следующее
действие» → push. Незапушенное теряется при пересоздании контейнера.
Перед push в открытый PR (не черновик) — целевые тесты затронутого, ruff + mypy, typecheck; полная проверка — CI (`/pr-precheck` отключён, указание заказчика 2026-11-25).
**Конец каждого этапа — PROGRESS.md в main** (указание заказчика 2026-11-25): последний подшаг плана этапа —
«PROGRESS этапа → main». До последнего push в PR этапа (вместе с кодом, не отдельным push одних *.md) обновить
PROGRESS.md: подшаги [x], «Сейчас» (этап закрыт при слиянии PR), «Следующее действие» (следующий этап), «Расход»,
«Блокеры и вопросы», «Допущения» — так main после слияния содержит актуальный прогресс. После слияния: `git fetch
origin main && git merge origin/main`, сверить PROGRESS.md в main (`git show origin/main:PROGRESS.md`); что
изменилось после слияния (номер слитого PR, итог CI) — первым коммитом ветки следующего этапа, в её PR. main напрямую
не правится.
После приёмки вехи и проекта первого этапа следующей (ADR и план в PROGRESS, всё запушено) — сигнал
заказчику «Готово к переходу» и продолжение в новой сессии (экономия окна; указание заказчика 2026-11-20).
При переходе в новую сессию: выключить страховку от лимита текущей сессии (`update_trigger` enabled=false), создать такую же для новой сессии (`create_trigger`, `persistent_session_id` = новая сессия, cron `22 * * * *`, тот же текст) и записать её номер в PROGRESS.md «Сейчас» (указание заказчика 2026-11-26).

## Git
- Ветка сессии `claude/…` → PR этапа в `main` (заголовок «Э<N>. <Название>», описание — Приложение Ж).
- Сливать после зелёного CI (`ci` и `windows`), merge commit; затем `git fetch origin main && git merge origin/main`.
- CI ждать событиями PR (подписка), не опрашивать. Упавшую проверку разбирает `ci-triager`; одна попытка перезапуска.
- `paths-ignore` у `pull_request` смотрит на весь diff PR: push одних `*.md` в открытый PR тоже запускает `ci` и `windows`.
- Экономия минут Actions: `ci` — только PR и push в main; `windows` — только PR не в черновике
  (или вручную, workflow_dispatch). PR держать черновиком, пока этап не готов; правки только docs/*.md CI не запускают.
- Бюджет Actions $25/мес (windows = 2× Linux; остаток — в PROGRESS.md):
  - Перед push в открытый PR — целевые тесты затронутых модулей, ruff + mypy, npm typecheck (полный локальный прогон
    `/pr-precheck` отключён указанием заказчика 2026-11-25; полный набор, E2E и bench проверяет CI). Push — только при зелёном.
  - Пушить в PR пачками, fix-коммиты копить; не плодить прогоны `ci`/`windows` по одному коммиту.
  - `windows` — один раз на готовом PR; перезапуск только после локально воспроизведённой и исправленной причины.
  - Остаток < $5 — не запускать `windows` вручную без согласования с заказчиком.

## Экономия токенов
- Читать только нужные файлы spec; ТЗ целиком не перечитывать.
- Поиск, логи, вывод тестов — через субагентов; короткие отчёты.
- Целевые тесты во время работы, полный набор — перед слиянием.
- Переносить код BF (docs/spec/pril-e-…md), не писать заново.
- Решение принято и записано в ADR — не обсуждать заново.

## Обязательные правила (полный список — раздел 17 ТЗ)
- Фирменный стиль во всём интерфейсе и **всех выпусках**: docs/brand/README.md (палитра, Montserrat/Inter, знак, иконка), ADR 0006.
- Тексты для пользователя — по-русски; идентификаторы и комментарии — по-английски.
- Координаты float64; float32 только для показа от целочисленного начала (ui/src/viz/origin.ts).
- Пропуски не превращать в ноль; ошибки — `{code, message, hint}` по-русски с подсказкой.
- Имена файлов не различаются только регистром; файл ≤ ~600 строк.
- Команда = запись в реестре (лента, Ctrl+K, клавиши, ассистент).
- Только собственные окна; никаких window.confirm/prompt/alert/open.
- Зависимости — только MIT/BSD/Apache-2.0/MPL-2.0/ISC/PSF (шрифты — OFL-1.1, ADR 0006); lock-файлы (core/uv.lock, package-lock.json);
  проверка `tools/ci/check_licenses_py.py`, `tools/ci/check_licenses_npm.mjs`.
- Ядро слушает только 127.0.0.1, токен `X-BF-Token`, проверка Host/Origin (core/bf_core/api/security.py).
- numba: `cache=True`; кеш — `NUMBA_CACHE_DIR` (bf_core/paths.py; в .exe — bf_core/numba_cache.py).
- multiprocessing только `spawn`; обработчики заданий регистрируются явным импортом.
- Готовность этапа — раздел 10.5 ТЗ.
