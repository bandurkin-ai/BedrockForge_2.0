## 6. Архитектура

### 6.1. Схема

    BedrockForge.exe (Electron, главный процесс)
     ├─ окно: React + TypeScript + three.js (протокол app://bedrockforge)
     │    └─ Web Workers: разбор двоичных массивов, LOD, подготовка геометрии
     ├─ preload (contextBridge): файлы, диалоги ОС, настройки, лицензия, обновление, safeStorage
     └─ запускает и контролирует → bf-core.exe (Python 3.12, FastAPI/uvicorn, 127.0.0.1:<порт>, токен)
            ├─ планировщик заданий → процессы-исполнители: очередь «тяжёлая» и «быстрая»
            ├─ проект: <Имя>.bfproj\  (project.sqlite, blobs\, cache\, logs\)
            └─ режим server (Э25): PostgreSQL 16 + общие blobs на сервере

### 6.2. Компоненты

| **Компонент**            | **Ответственность**                                                                                                                                                                                                               | **Не делает**               |
|--------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------|
| Главный процесс Electron | Окно, заставка, жизненный цикл ядра (запуск, проверка готовности, перезапуск, завершение дерева процессов через Job Object), протокол `app://`, системные диалоги, лицензия (проверка подписи), обновление, хранение ключа Claude | Расчёты, доступ к БД        |
| Интерфейс (renderer)     | Лента, дерево, панели, окна, 3D-сцена, графики, редактор стрингов, макеты печати                                                                                                                                                  | Прямой доступ к файлам и ОС |
| Ядро `bf-core`           | Форматы, БД проекта, расчёты, задания, ассистент Claude (вызовы API), экспорт                                                                                                                                                     | Отрисовку                   |
| Исполнители              | Тяжёлые операции в отдельных процессах (`multiprocessing`, контекст `spawn`)                                                                                                                                                      | Доступ к UI                 |

### 6.4. Жизненный цикл процессов

| **Шаг**        | **Требование**                                                                                                                                                                           |
|----------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Старт          | Заставка Electron ≤ 1 с; главный процесс запускает `bf-core.exe --port 0 --token <случайный> --data <путь>`                                                                              |
| Готовность     | Ядро печатает в stdout `BF-READY port=<n> version=<v>`; оболочка проверяет `GET /api/v1/health` и совпадение версий; окно показывается, когда рабочая область нарисована (одна заставка) |
| Работа         | Интерфейс обращается к ядру по `http://127.0.0.1:<n>` с токеном; события — SSE `/api/v1/events`                                                                                          |
| Сбой ядра      | Перезапуск до 3 раз за 5 мин с сообщением; затем окно «Ядро не запускается» с журналом                                                                                                   |
| Завершение     | `POST /api/v1/shutdown`, ожидание 10 с, затем принудительное завершение дерева процессов (Job Object `KILL_ON_JOB_CLOSE`)                                                                |
| Один экземпляр | Повторный запуск активирует существующее окно; открытие `.bfggis`/`.bfproj` двойным щелчком передаётся в него                                                                            |

### 6.5. Хранение данных

**Папка проекта** `<Имя>.bfproj\` (место выбирает пользователь; по умолчанию `Документы\BedrockForge\Проекты`):

| **Путь**               | **Содержимое**                                                                                                      |
|------------------------|---------------------------------------------------------------------------------------------------------------------|
| `project.sqlite`       | Метаданные, таблицы скважин, журналы правок, стили, графики, результаты; WAL                                        |
| `blobs\ab\cd\<sha256>` | Неизменяемые двоичные файлы по SHA-256: массивы каркасов, линий, растры, исходные загрузки, Parquet блочных моделей |
| `cache\`               | Производные данные (LOD, тайлы, индексы); можно удалить без потерь                                                  |
| `backups\`             | Автокопии `project.sqlite` (5 последних)                                                                            |
| `logs\`                | Журналы заданий проекта                                                                                             |

**Профиль пользователя:**

| **Путь**                               | **Содержимое**                                                                |
|----------------------------------------|-------------------------------------------------------------------------------|
| `%APPDATA%\BedrockForge\settings.json` | Настройки интерфейса, горячие клавиши, последние проекты, состояние раскладки |
| `%APPDATA%\BedrockForge\license\`      | Файл лицензии, отметки пробного периода                                       |
| `%LOCALAPPDATA%\BedrockForge\cache\`   | Кеш numba, временные файлы                                                    |
| `%LOCALAPPDATA%\BedrockForge\logs\`    | Журналы оболочки и ядра                                                       |

**Правила:**

- Доступ к `project.sqlite` — только через ядро (одна запись, много чтений); второй экземпляр приложения открывает проект «только чтение» с предупреждением (блокировка файлом `project.lock`).

- Большие таблицы (пробы до 5 млн строк) — в SQLite с индексами `(set_id, hole_id, from_m)`; для статистики выгружаются в Arrow без копий в памяти, где возможно.

- Блочные модели — Parquet (zstd), строки в порядке кода Мортона IJK, группы ~1 млн строк; запросы — DuckDB; описание и атрибуты — в SQLite.

- Каркасы — float64 вершины и uint32 треугольники (`.npy`, `mmap`), части по ~64 тыс. треугольников, 3 уровня LOD (1, 1/8, 1/64), BVH.

- Ссылки между объектами (например, Swath → блочная модель) — через таблицу `object_refs`; экспорт/импорт `.bfggis` пересчитывает идентификаторы по ней.

- Сборщик неиспользуемых blobs — по таблице владельцев; новый тип с файлами обязан зарегистрировать владельца (иначе тест падает).

- Миграции Alembic — обратимые (`downgrade`), проверяются на копии реального проекта; работают на SQLite (batch mode) и PostgreSQL.

- Диалект-зависимый SQL — только в `core/bf_core/db/dialect.py`; тесты БД идут на обоих диалектах в CI.

### 6.6. Внутренний API ядра

| **Правило**     | **Значение**                                                                                                                                                                    |
|-----------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Транспорт       | HTTP/1.1 на `127.0.0.1`, префикс `/api/v1`                                                                                                                                      |
| Форматы         | JSON (pydantic-модели); массивы — `application/octet-stream` (little-endian, C-порядок) с `Range` и `ETag`; события и прогресс — SSE                                            |
| Типы на фронте  | Генерируются из OpenAPI (`openapi-typescript`) — ручного дублирования моделей нет                                                                                               |
| Ошибки          | `{code, message, hint}`; `message` и `hint` — по-русски, что случилось и как исправить; 409 — конфликт версии; 422 — предусловия операции; 500 — общий текст + ссылка на журнал |
| Версии объектов | Изменяемые объекты имеют `version`; запись с устаревшей версией — 409                                                                                                           |
| Справочник      | 143 эндпоинта BF (README и код `api/app/routers`) — ориентир для набора операций; пути BF2 могут отличаться                                                                     |

### 6.7. Задания

| **Требование**        | **Значение**                                                                                                                                                                                          |
|-----------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Хранение              | Таблица `jobs` в `project.sqlite`: вид, параметры, статус, прогресс, журнал, результат, попытки, времена, очередь                                                                                     |
| Очереди               | `heavy` (импорт, кригинг, карьер, RBF, экспорт) — параллельно min(ядра − 1, ОЗУ / 3 ГБ), не меньше 1; `quick` (операции с линиями и каркасами, предпросмотр) — 1 исполнитель, никогда не ждёт тяжёлых |
| Исполнители           | Процессы `spawn`; регистрация обработчиков — явным импортом модуля (не из `__main__`); тест с настоящими процессами                                                                                   |
| Отмена                | Кооперативная: обработчик вызывает `tick(progress)` не реже раза в 1 с; отмена внутри большого блока работает                                                                                         |
| Память                | Перед запуском — оценка памяти задания; ограничение процесса через Job Object; при превышении — понятная ошибка                                                                                       |
| После перезапуска     | `running` → `queued`, попытка +1; импорт — не больше 2 попыток                                                                                                                                        |
| Интерфейс             | Вкладка «Задания»: очередь, почему ждёт, прогресс, отмена, повтор, журнал (копировать / сохранить `.txt`)                                                                                             |
| Исходный файл импорта | Копируется в `blobs` последним шагом задания                                                                                                                                                          |

### 6.8. 3D и графика на встроенной видеокарте

| **Требование**   | **Значение**                                                                                                                                             |
|------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| API              | WebGL2 (three.js); WebGPU — не в v1                                                                                                                      |
| Координаты       | float32 относительно начала объекта (раздел 5.4)                                                                                                         |
| Отрисовка        | Кадр только при изменении; отбор по пирамиде видимости; без `preserveDrawingBuffer` (снимок — отдельным проходом)                                        |
| Скважины         | 50 тыс. стволов — объединённая геометрия частями, подписи по масштабу и плотности                                                                        |
| Каркасы          | LOD по экранному размеру, бюджет треугольников в кадре (по умолчанию 8 млн для встроенной графики, 30 млн для дискретной; настраивается)                 |
| Блочные модели   | Только видимые грани (оболочка), срезы, фильтры; цвет через текстуру легенды; \> 5 млн граней — объединение до родительских блоков с пометкой «упрощено» |
| Бюджет памяти    | Менеджер бюджета: GPU-ресурсы ≤ 1,5 ГБ на встроенной графике; выгрузка невидимых LOD                                                                     |
| Потеря контекста | Обработка `webglcontextlost`/`restored` без перезапуска                                                                                                  |
| Выбор            | three-mesh-bvh для луча, уточнение в ядре по float64                                                                                                     |
| Сглаживание      | Настройка: MSAA вкл/выкл, плотность пикселей 0,75–2                                                                                                      |

### 6.9. Реестр команд (единый источник)

- Каждая функция — команда в реестре: `id`, название (рус.), группа, иконка, горячая клавиша, условие доступности с текстом причины, `confirm` (меняет данные), `uiOnly` (требует человека), обработчик.

- Из реестра строятся: лента, палитра `Ctrl+K`, горячие клавиши и окно их назначения, контекстные меню дерева, инструменты ассистента Claude (JSON-схема генерируется).

- Команды регистрируются модулями (автоподключение по папкам), а не правкой одного общего файла — чтобы параллельная работа не конфликтовала.

### 6.10. Ассистент Claude (Э23)

- Вызовы Anthropic API из ядра (Python SDK); ключ API передаётся из оболочки (`safeStorage`) на время сеанса.

- Выбор модели и уровня усилий, сохранённые диалоги в проекте, учёт расхода (токены, оценка стоимости).

- Инструменты ассистента — команды реестра (чтение данных проекта компактными сводками и постранично; изменения — с подтверждением пользователя).

- Без интернета — панель показывает «Ассистент недоступен без интернета», остальное работает.

- MCP-сервер не реализуется.

### 6.11. Сервер ЛВС (Э25)

| **Требование**    | **Значение**                                                                                                                          |
|-------------------|---------------------------------------------------------------------------------------------------------------------------------------|
| Состав            | Тот же `bf-core` с `BF_MODE=server`, PostgreSQL 16, общий каталог blobs; служба Windows (или Linux systemd)                           |
| Пользователи      | Логин/пароль (argon2id), сессии; роли `admin`, `editor`, `viewer`; права на проект                                                    |
| Совместная работа | Блокировка объекта на время правки (аренда 5 мин с продлением); остальные видят «Правит \<имя\>»; версии объектов и 409 при конфликте |
| Передача файлов   | Загрузка частями 16 МБ с SHA-256 каждой части и докачкой; выдача по `Range`                                                           |
| Журнал            | Кто, когда, что изменил; экспорт журнала                                                                                              |
| Клиент            | Окно «Подключение к серверу»: адрес, вход, список проектов; локальные проекты доступны как раньше                                     |
| Развёртывание     | `docs/SERVER.md`: установка, резервные копии (`pg_dump` + blobs) с проверкой восстановления, обновление                               |

### 6.12. Структура репозитория

    /app/        Electron: main, preload, протокол, лицензия, обновление (TypeScript)
    /ui/         Интерфейс: shell/ (лента, дерево, панели, окна, реестр), viz/ (3D), charts/, edit/, modules/<модуль>/
    /core/       Python: bf_core/{api,db,formats,importing,exporting,archive,jobs,geo,lines,blocks,stats,geostat,model,mine,print,qaqc,license,assistant}
    /core/tests/ pytest; tests/data/real/ — файлы real_data; генераторы — tools/gen/
    /bench/      Замеры и budgets.json
    /tools/      bf-license, генераторы синтетики, скрипты сборки
    /docs/       spec/ (ТЗ по разделам), adr/ (решения), LICENSING.md, SERVER.md, USER_GUIDE.md, CHECKLIST.md
    /.claude/    agents/, hooks/, settings.json
    /.github/    workflows: ci.yml (Linux), windows.yml (сборка и E2E), release.yml
    CLAUDE.md, PROGRESS.md, README.md, CHANGELOG.md

Правила структуры:

- Модуль = папка в `core/bf_core/<модуль>` + `ui/src/modules/<модуль>` + тесты рядом; роутеры и команды подключаются автоматически.

- Стили — CSS-модули на компонент, общий файл стилей не дописывается.

- Файл кода ≤ ~600 строк; логика — в чистых модулях без React и three.js (тестируются в node).

- Имена файлов, различающиеся только регистром, запрещены (проверка в CI).
