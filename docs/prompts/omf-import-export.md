# Промт: импорт и экспорт формата OMF v1

Этот файл — задание на реализацию. Сначала прочитай `docs/HANDOFF.md`, `docs/FORMATS.md` и `docs/ROADMAP.md` (этапы 9, 12, 27) и следуй принятым там договорённостям.

## 1. Цель

Реализовать импорт и экспорт формата OMF (Open Mining Format) v1 в BedrockForge.

OMF — открытый формат обмена между горными ГИС. Leapfrog Geo читает и пишет только OMF v0.9 (это файловый формат v1), поэтому цель — v1 в обе стороны. Формат v2 из репозитория `bandurkin-ai/omf-python` — альфа-диалект, не совпадающий с официальным OMF 2.0-beta (`gmggroup/omf-rust`); его не пишем и в этой задаче не читаем.

## 2. Почему свой читатель и писатель

Библиотеку `omf` в зависимости `api` не добавляй: она требует `numpy<2` и пакет `properties`, который не собирается на Python 3.12+, а BedrockForge работает на Python ≥ 3.12 и numpy ≥ 2. Читатель и писатель пишутся свои, как остальные форматы в `api/app/formats/`.

Спецификацией служит код `omf-python`: `omf/compat/omf_v1.py` (полный читатель v1) и файл `assets/v1/test_file.omf` (93 КБ, MIT) — скопируй его в тестовые данные `api`. В нём PointSet с двумя текстурами, LineSet, Surface с треугольниками, Surface с гридом и Volume, у всех числовые данные.

## 3. Формат v1 кратко

| Часть | Содержимое |
|---|---|
| Заголовок | 4 байта `84 83 82 81`; 32 байта версии, начинается с `OMF-v0.9.0`; 16 байт UUID проекта; uint64 little-endian — смещение JSON |
| Двоичные блоки | Между заголовком и JSON, каждый сжат zlib |
| JSON | От смещения до конца файла: словарь `uid -> объект` с полем `__class__`; объекты ссылаются друг на друга по uid |
| Числовые массивы | `ScalarArray`, `Vector2Array`, `Vector3Array`, `Int2Array`, `Int3Array` задают блок как `{start, length, dtype}` |
| Списки в JSON | `StringArray`, `DateTimeArray`, `ColorArray` хранят значения прямо в JSON |
| Изображения | Блок с `dtype` `image/png` |
| Элементы | `PointSetElement`, `LineSetElement`, `SurfaceElement` (геометрия треугольная или грид), `VolumeElement` (тензорная сетка: `tensor_u/v/w`, `axis_u/v/w`, `origin`) |
| Данные элемента | `ScalarData`, `Vector2Data`, `Vector3Data`, `StringData`, `ColorData`, `DateTimeData`, `MappedData` (индексы плюс легенды); у каждого есть `location` |

Имена полей и остальные детали бери из `omf_v1.py`, не угадывай.

Порядок ячеек тензорной сетки: в `omf-python` индекс считается через `ravel_multi_index` с `order="F"` (i меняется быстрее всех), и читатель v1 массивы не переставляет. Подтверди это тестом на тестовом файле и на синтетической сетке с несимметричными размерами, прежде чем полагаться на порядок.

## 4. Соответствие объектов

| OMF v1 | BedrockForge | Что теряется |
|---|---|---|
| `SurfaceElement` (треугольники) | `Wireframe` через `add_wireframe` | Данные на вершинах и гранях |
| `SurfaceElement` (грид) | `Wireframe`, сетка триангулируется | То же |
| `LineSetElement` | `LineLayer`: сегменты склеиваются в полилинии | Данные на вершинах и сегментах |
| `VolumeElement` | Набор `blocks` через `store_block_model` | Повёрнутые модели не импортируются |
| `ScalarData` на ячейках | `Column(kind="number")` | — |
| `MappedData` + легенда | `Column(kind="category")`, `labels` | Цвета легенды |
| `PointSetElement` | Нет сущности (точки — этап 9) | Весь элемент |
| Текстуры | Не переносятся | Изображения |
| `color` элемента | `"#rrggbb"` | — |
| `origin` проекта и элемента | Прибавляется к координатам | — |

## 5. Импорт

1. `api/app/formats/omf.py`: читатель v1, возвращающий структуры, которые уже понимает код импорта — `Mesh` (`formats/wireframes.py`), `LineLayer` и `Polyline` (`formats/lines.py`), `BlockTable` и `Column` (`formats/blockmodel.py`, `formats/micromine.py`) — плюс список предупреждений. Ошибки формата — свой класс исключения с сообщением для пользователя на русском, как `WireframeFormatError`.
2. Правила перевода:
   - `SurfaceElement` с треугольниками → `Mesh`. Грид триангулируй (два треугольника на ячейку, учитывай `offset_w` и оси).
   - `LineSetElement` → `LineLayer`: сегменты склей в полилинии по общим вершинам; замкнутость определяй как в остальных читателях линий.
   - `VolumeElement` → `BlockTable`: центры и размеры всех ячеек, данные на ячейках — в `Column` (`ScalarData` → number, `MappedData` → category с `labels` из легенды, пустое = −1). Оси, совпадающие с осями координат с точностью до перестановки и знака, поддержи; повёрнутую модель не импортируй и объясни причину — в BedrockForge блоки без поворота.
   - Ко всем координатам прибавляй `origin` проекта и элемента. Координаты только float64.
   - Цвет элемента → `"#rrggbb"`.
   - `PointSetElement`, текстуры, данные на вершинах, гранях и сегментах сейчас некуда положить: пропускай и пиши по одному предупреждению на элемент с его именем.
3. `api/app/formats/registry.py`: `detect()` распознаёт `.omf` по расширению и сигнатуре и возвращает новый вид `omf`. `api/app/formats/inspect.py`: предпросмотр читает только заголовок и JSON (без двоичных блоков) и показывает элементы, их типы и размеры, а также что будет пропущено.
4. `api/app/importing/omf.py` и обработчик задания `import.omf` в `api/app/jobs/handlers.py`. Один файл создаёт несколько наборов: один набор `wireframes` со всеми каркасами, один набор `lines` со слоем на каждый LineSet, по набору `blocks` на каждый Volume. Используй `add_wireframe`, `add_line_layer`, `store_block_model` и `queue_derive`. Соблюдай порядок из `import_objects`: исходный файл переносится в хранилище последним шагом, после которого ничего не может упасть; `blobs.put_file` забирает файл, поэтому вызови его один раз и запиши полученный хеш в `source` всех созданных наборов. Предупреждения читателя пиши в журнал задания через `ctx.log` с уровнем `warning` и в `meta` наборов.
5. `api/app/routers/jobs.py`: вид `omf` в `ImportIn`, и `start_import` ставит задание `import.omf`.
6. `web/src/shell/ImportWizard.tsx`: вид `omf` в `ObjectKind`, `KIND_TITLES` и `planJobs`, показ предпросмотра состава.

## 6. Экспорт

1. Писатель v1 в `api/app/formats/omf.py`: каркасы → `SurfaceElement`, слои линий → `LineSetElement` (атрибуты линий — на сегментах, если это выразимо, иначе предупреждение), регулярная блочная модель → `VolumeElement` с плотной сеткой по `meta.grid`, отсутствующие ячейки = NaN, категории → `MappedData` с легендой. Субблочную модель в v1 выразить нельзя: не экспортируй её и сообщи об этом. Перед построением плотной сетки проверь её размер и откажись с понятным сообщением, если она не помещается в разумную память.
2. Задание `export.omf`: параметры — проект и список наборов. Экспорта объектов в продукте ещё нет, поэтому спроектируй выдачу файла: результат задания не входит во владельцев blob (`api/app/storage/gc.py`), и файл из хранилища был бы удалён сборкой мусора. Положи файл в отдельную папку внутри `DATA_DIR` со сроком жизни и чисткой в `gc.collect` и добавь эндпоинт скачивания по заданию с именем файла. Если видишь вариант проще и надёжнее — предложи его до реализации.
3. Веб: команда экспорта в `web/src/shell/commands.ts`, пункт в ленте и в контекстном меню дерева; ход и ссылка на файл — во вкладке «Задания». Диалоги только через `shell/dialogs.tsx`.

## 7. Тесты

Тесты API идут на PostgreSQL (см. `api/tests/conftest.py` и раздел «Запуск» в HANDOFF).

- Читатель: тестовый файл v1 — число элементов, размеры массивов, охваты, значения данных.
- Round-trip писатель → читатель: координаты совпадают побитно (требование 2.3 плана), атрибуты и легенды совпадают, цвета сохраняются.
- Импорт через API: загрузка, detect, задание, появление наборов трёх видов, предупреждения о пропущенных точках и текстурах.
- Экспорт через API: задание, скачивание, файл читается своим читателем.
- Негативные: не OMF, обрезанный файл, битый zlib-блок, неизвестная версия, повёрнутая модель, субблочная модель на экспорт.
- Сверка с эталонной библиотекой: в отдельном окружении Python 3.11 с `numpy<2` и `setuptools<70` установи `omf-python` и проверь, что `omf.load` открывает экспортированный файл и проходит `validate()`. Это разовая проверка разработчика, в CI и зависимости её не включай.
- Веб: тесты `planJobs` для вида `omf`; `npm test` и `npx tsc --noEmit` проходят.
