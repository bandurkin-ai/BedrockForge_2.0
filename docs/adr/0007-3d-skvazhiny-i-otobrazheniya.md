# ADR 0007. 3D-окно: скважины, разрезы, отображения по стволу, стили, каротаж

**Статус:** Принято, 2026-11-17 (Э6; проект — architect). Основа 3D — ADR 0004 (не пересматривается); схема — ADR 0003 (дополняется миграцией 0004).

## Контекст

- ТЗ 7.13–7.17, 6.8, 7.0.10; 5.3: открытие проекта ≤ 5 с до первого кадра, 50 тыс. стволов ≥ 20 кадров/с на встроенной графике; 5.4: float64, на видеокарте ≤ 0,5 мм.
- В BF2 есть: `ui/src/viz/origin.ts`, спайк `ui/src/spikes/mesh.ts`, объявленные команды `scene.*`, `section.*`, `holes.*`, `chart.striplog`; `scene.style` и `layer.show` пишут только в store; `Viewport` — заглушка. Ядро: `drillholes/trajectory.py` (кеш траекторий по версии набора), `desurvey.py` (`positions`, `sample_paths`), `snapshot.py` (снимки таблиц колонками), `audit/service.py` (`latest`, `findings`), `settings(scope, key, value, version)`. Таблиц `styles` и `charts` нет.
- BF: `scene3d.ts` — 2987 строк, `SceneView.tsx` — 972, `downholeGeometry.ts` — 788, `DownholeForm.tsx` — 544. Траектории идут в JSON с округлением до 1 см (нарушает 5.4), интервалы — в JSON по скважинам (5 млн строк так не передать); двоичный формат «snap» уже был (`viz.py /snap`).
- Найдено при проектировании: в `archive/spec.py` таблица `settings` целиком помечена `view=True`, поэтому при экспорте без настроек вида теряются справочники кодов (`codes`, `code_links`, Э4). Кроме того, id в ключах настроек при импорте `.bfggis` не перенумеровываются.

## Решение

### 1. Геометрия скважин: модуль ядра `viz`, двоичный формат BFA1

| Тема | Решение |
|------|---------|
| Контейнер BFA1 | `application/octet-stream`: 4 байта `BFA1`, затем `u32` — длина заголовка, сам заголовок (JSON, UTF-8) и нули до границы 8 байт. Дальше идут массивы, перечисленные в заголовке как `[имя, dtype, count, offset]`: little-endian, C-порядок, offset кратен 8. Worker получает представления без копирования (ADR 0004 §4). Типы: `<f8 <f4 <i4 <u4 <u2 <u1`. Ошибки — JSON `{code, message, hint}` |
| Части | Скважины набора упорядочены по коду Мортона устья (ячейка 50 м) и режутся по ≤ 2000 стволов. Часть шире 16 км по любой оси делится ещё (ADR 0004 §2). Начало части — целый метр у центра её охвата, хранится в заголовке как float64 |
| ETag | Для производных данных ETag — это SHA-256 ключа, а не тела. В ключ входят: формат, uid проекта, набор, `objects.version`, сумма `rev` таблиц, метод, параметры, часть, `run_id` аудита. Повторный запрос получает 304 без расчёта; `Cache-Control: no-cache`. Это уточнение ADR 0004 §4, где ETag описан для blobs. Range не нужен: каждая часть запрашивается отдельно, одновременно — не больше 4 |
| Обновление | После правки, импорта или удаления (`data.refresh`, события заданий) окно перезапрашивает манифест с `If-None-Match`. Удалённый набор сразу исчезает из 3D (17.4.7) |
| Порядок загрузки | Манифест → устья (первый кадр) → пути частей, первыми — ближайшие к центру экрана → отображения |

| Запрос (`/api/v1/viz`) | Ответ |
|------------------------|-------|
| `GET /sets/{id}/holes?method=` | BFA1 `holes`. Заголовок: `version`, `method`, `parts[{k, n, bbox[6] f64, origin[3], etag}]`, `names[]`, `skipped[]`, `audit {run_id, stale, at}` или null. Массивы по скважинам: `id u4`; `collar f8×3` — абсолютные float64 для мини-плана, разрезов и авто-разреза; `td f8`; `length f8`; `plan_az f4` — азимут от устья к забою в плане, NaN у вертикальной (смещение < 0,1 м); `kind u1` — 0 скважина, 1 канава, 2 проектная (по `hole_type` Э4); `audit u1`; `part u2`; `slot u2` |
| `GET /sets/{id}/paths/{k}?method=&tol=0.01` | BFA1 `paths`: `offsets u4 (n+1)`, `xyz f4×3` от начала части, `md f8`. Точки — станции плюс сгущение дуги минимальной кривизны с шагом √(8·R·tol): хорда отходит от дуги не больше `tol` (по умолчанию 1 см). Прямой участок — 2 точки. Данные только для показа |
| `GET /sets/{id}/intervals/{k}?table=<name_key>&fields=AU,CU` | BFA1 `intervals`: строки части по порядку (скважина, «от»). Массивы: `slot u2`, `from f8`, `to f8` (у событий NaN). На каждое поле: число — `v:<поле> f8`, NaN означает «пусто», а не 0; текст — `c:<поле> i4` (−1 — пусто) со словарём части `cats {поле: [значения]}` в заголовке. Полей ≤ 16. Источник — снимок `snapshot.py` и индекс строк по скважинам в кеше снимка |
| `GET /sets/{id}/field-stats?table=&field=` | JSON: `count, missing, min, max, p02, p50, p98, p99`; гистограммы на 48 корзин (линейная и логарифмическая); категории `[{value, count, length}]` ≤ 1000. Нужен для «Шкалы», «Цвета» и редактора градаций |
| `POST /sets/{id}/class-counts` `{table, field, bounds[]}` | `{counts[], lengths[]}` — «число и доля проб» в классе по всем данным, а не по загруженным частям |
| `POST /sets/{id}/log` | Окно 7.17 (§6) |

| Тема | Решение |
|------|---------|
| Интервалы → точки | Пересчёт в Worker на клиенте: «от» и «до» переводятся в точки линейной интерполяцией по `md` вдоль ломаной части, с промежуточными вершинами (как `pointAt` и `pathBetween` в BF). Погрешность ≤ `tol`. Подписи глубин и шаблоны `{from}`, `{to}` берутся из чисел f8, не из геометрии |
| Цвет устьев по аудиту | `audit u1`: 0 — аудита нет, 1 — без находок, 2 — замечания, 3 — предупреждения, 4 — ошибки. Это худшая важность среди находок последнего прогона, один запрос `GROUP BY hole`. Цвета берутся из темы (в BF: `#c0392b`, `#e0a030`, `#3b82d6`, `#2e9d57`, нет аудита — `#9aa3b5`). Если аудит устарел, в легенде появляется плашка «устарел», цвета остаются |

### 2. Настройки вида проекта (7.0.10)

| API | Ответ |
|-----|-------|
| `GET /api/v1/view` | `{values: {key: {value, version}}}` — все ключи scope `view`, уже нормализованные |
| `PUT /api/v1/view/{key}` `{value, expected_version}` (для нового ключа — 0) | 200 `{value, version}`; 409 `version_conflict` с текущими `{value, version}`; 422 `bad_view_setting` — по-русски, с подсказкой. Значение ≤ 512 КБ |

| Ключ | Значение | Лимит и нормализация |
|------|----------|----------------------|
| `scene` | `{perspective, grid, vexag из 1, 2, 3, 5, wireframe_opacity 0,1–1}` | Значение вне пределов заменяется умолчанием (0,7) |
| `section` | `{line, clip}`, где `line` — `{x0, y0, az [0; 360), length > 0 или null, towards ≥ 0, away ≥ 0}` или null | `clip` без линии → false |
| `hidden` | Ключи `set:<id>`, `set:<id>:collars`, `set:<id>:paths`, `set:<id>:intervals`, `wf:<id>`, `ln:<id>`, `rs:<id>`, `bm:<id>` | ≤ 2000, без повторов, хранятся последние; при чтении ключи удалённых объектов отбрасываются |
| `displays` | `[{chart, visible}]` — включённые сохранённые отображения по порядку | ≤ 200 |
| `swaths` | Резерв (Э13) | ≤ 50 |
| `collar_styles`, `trace_styles` | `{"<набор>": CollarStyle или TraceStyle}` (BF `collarStyle.ts`, `traceStyle.ts`) | ≤ 200 каждого вида; лишние удаляются: сначала стили удалённых наборов, потом самые старые |
| `block_styles` | Резерв (Э17) | ≤ 200 |
| `columns` | `{"<набор>:<таблица>": [колонки]}` — открытые колонки панели «Таблица» | ≤ 200 таблиц × 500 колонок |
| `active` | `{set, hole, table}` (маршрут `#/?set=3&hole=…&table=assay`) | Несуществующее → null |

| Тема | Решение |
|------|---------|
| Нормализация | В ядре (pydantic, `viewstate/keys.py`). Чтение мягкое: значения зажимаются в пределы, лишнее отбрасывается, неизвестные ключи игнорируются — старый проект не ломается. Запись строгая — 422. Интерфейс повторяет нормализацию (`normalizeView` уже есть), чтобы откликаться сразу |
| Запись | Клиент пишет каждый ключ с задержкой 400 мс; store — только кеш, источник — проект. При 409 клиент берёт серверное значение, заново применяет к нему своё изменение (для `hidden` — операцию «добавить» или «убрать», для остальных ключей — замену полей) и повторяет запрос один раз. Второй 409 — клиент принимает серверное значение и сообщает об этом в строке состояния |
| Сервер (Э25) | Scope `view@<uid пользователя>`; на Э6 — просто `view` |
| Профиль пользователя | Всё из первой строки 7.0.10 (включая «мини-план показан/скрыт») и настройки графики: MSAA, плотность пикселей, класс графики, бюджеты треугольников и памяти, счётчик кадров. Это свойства ПК, а не проекта |
| `.bfggis` | В `archive/spec.py` необязательным остаётся только scope `view`; `codes`, `code_links` и остальные scope копируются всегда. При импорте `archive/view_remap.py` перенумеровывает id в ключах и значениях `view` (`set:`, `wf:`…, `displays.chart`, ключи стилей наборов, `active.set`) и в ключах `code_links`. Ненайденные id отбрасываются |

### 3. Отображения по стволу и библиотека стилей (7.16)

| Тема | Решение |
|------|---------|
| Миграция `0004_e6_styles_charts` | Таблица `styles`: `id`, `uid` (32 символа, уникален), `name`, `name_key`, `level` (`palette` — раскраска, `layer` — стиль слоя, `display` — шаблон), `data_kind` (`number`, `text`, `event`, `mixed`), `body` (JSON ≤ 256 КБ), `default_for` (JSON, ≤ 50 масок), `extra` (JSON), `version`, `author`, времена; уникальность `(level, name_key)`. Таблица `charts` (ADR 0003, перенесена с Э13): `object_id` (PK → `objects`, CASCADE), `kind`, `settings` (JSON), `auto_name`. Обе таблицы — в `archive/spec.py`: `styles` перенумеровывается, `charts.object_id` ссылается на `objects` |
| Сохранённое отображение | `objects(kind="chart", parent_id=<набор>)` плюс строка `charts(kind="striplog")`. В дереве — строкой под «Стволами» набора; версия — `objects.version` (при конфликте 409). До «Сохранить» черновик живёт только в памяти окна — не в дереве и не в настройках. Закрытие с несохранённым — собственный диалог (17.4.6) |
| `charts.settings` (`striplog`, `v: 1`) | Модель BF `StripLogSettings` и `Track` (перенос `charts/stripLog.ts`) с изменениями. `table` — это `dh_tables.name_key`, а не id: так ссылка переживает замену таблицы и `.bfggis`. `holes` — `"all"` или список имён. Ссылки `style`, `palette`, `template` — `{uid, name, linked, modified?}`. Слоёв ≤ 32, объём ≤ 256 КБ. Чтение — через `withDefaults`, старые версии нормализуются |
| Связь 🔗 | Слой всегда хранит копию настроек. При `linked` тело стиля из библиотеки накладывается на копию при показе (`resolveTracks`, BF), поэтому правка стиля сразу перестраивает все связанные отображения. При удалении стиля ядро в одной транзакции вливает его последнее тело в копии слоёв (поверхностное слияние ключей уровня), снимает связь и возвращает список изменённых отображений — их вид не меняется. Правило слияния задают общие фикстуры `core/tests/data/styles/*.json`, по ним проверяют и pytest, и vitest |
| Умолчание по маске | `default_for` — маски без учёта регистра, с `*` и `?` (`AU`, `AU*`). При добавлении поля из любой таблицы берётся самый точный стиль подходящего `data_kind`: точное имя, затем меньше `*`, затем длиннее литеральная часть, затем более новый. Маска `AU*` ловит `AU_CUT` |
| Встроенные стили | Константа интерфейса (BF `BUILTIN_STYLES`: столбцы, градации, ступени, линия, трубка по шкале, лента по градациям, литология, события). `uid = builtin:<ключ>`, только чтение; в БД и в файл не пишутся |
| `.bfstyle.json` | Формат BF без изменений: `{"format": "bedrockforge-styles", "version": 1, "styles": [{uid?, name, level, data_kind, body, default_for, …extra}]}`. BF2 добавляет `uid`, файлы BF читаются. Импорт — до 1000 стилей и 4 МБ. Конфликт имён по ключу `level:name` решается так: `replace`, `keep_both` (имя «… (2)», новый uid) или `skip` |
| API | `/api/v1/styles`: `GET ?level=`, `POST`, `PATCH /{id}` (с `expected_version`), `DELETE /{id}` (с отвязкой), `GET /{id}/usage` («Где используется» — просмотр `charts` вида `striplog`), `POST /export {ids}` (текст файла), `POST /import {file, conflicts, default}`. `/api/v1/charts`: `POST` (отображение набора), `GET`, `PUT` и `DELETE /{object_id}` |
| Раскраски для БМ | Те же записи `styles(level=palette)`; применение — на Э17 |

### 4. Разрезы (7.14): чистая математика в `ui/src/viz/section/`

| Функция | Решение (float64, без three) |
|---------|------------------------------|
| Линия | `SectionLine {x0, y0, az, length или null, towards, away}` (BF `geometry.ts`). Азимут — по часовой от севера; нормаль направлена вправо от линии, наблюдатель — на её стороне |
| Два клика | Луч из пикселя (float64) пересекается с плоскостью через центр вида: в плане — с горизонтальной `z = target.z`, сбоку — с вертикальной, перпендикулярной взгляду. `x0, y0` — первая точка, `az` — азимут от первой ко второй, `length = null`. Резинка — `#ff8c1a`. После второго клика: `clip = true`, вид `section`, линия вписывается от края до края охвата видимых объектов |
| Окно и профили | По умолчанию 25 и 25 м. `[` и `]` сдвигают `x0, y0` по нормали ровно на ±(towards + away); тест проверяет равенство в float64 |
| Через скважину | `x0, y0` — устье, `az` — `plan_az` из ядра; у вертикальной (NaN) азимут остаётся прежним |
| Авто-разрез | Главная ось устьев (PCA по XY, BF `defaultSection`): линия через центр устьев поперёк простирания |
| Отсечение | 2 плоскости (4, если задана длина) считаются в float64 от начала сцены. Один общий массив `clippingPlanes` раздаётся материалам отсекаемых слоёв: скважин, отображений, подписей, позже — линий, БМ и каркасов. Не отсекаются линия разреза, мини-план, гизмо и вертикальный растр-подложка (Э7). Сечения каркасов — Э8 |
| Вид в плоскость | Z вверх, линия слева направо, камера — с положительной стороны нормали. «Вписать» при отсечении учитывает только объекты в окне (17.4.10); near и far пересчитываются каждый кадр |
| Мини-план | SVG (перенос `SectionMap.tsx`): устья и данные до 20 000 точек (больше — равномерное прореживание с пометкой «упрощено»), линия, окно, оранжевый треугольник стороны взгляда. Клики на мини-плане тоже рисуют линию; крестик и кнопка «План» — команда `section.plan` |

### 5. Пересечения стволов с каркасами и блоками (7.15)

| Сейчас (Э6) | Позже |
|-------------|-------|
| `TraceStyle` целиком: риски, глубина на забое, пересечения «по видимым» или «по всем». Слой меток ◆ ▲ ■ с подписью «глубина · объект» и приоритетом подписей: пересечения, затем глубина забоя, затем номера, затем риски. ### 6. Окно «Данные по скважинам» (7.17)

| Тема | Решение |
|------|---------|
| `POST /api/v1/viz/sets/{id}/log` `{holes ≤ 30, tables: [{table, fields}], from?, to?}` | JSON по скважинам: `name`, `collar_z`, `td`; по таблицам — `from[]`, `to[]`, `values {поле: […]}` (null — пусто). До 20 000 строк на скважину и таблицу, при обрезке — флаг `truncated`. 31 скважина → 422 `too_many_holes`; в интерфейсе флажок 31-й скважины недоступен |
| Интерфейс | Перенос `StripLogWindow.tsx`, `StripLogChart.tsx` (SVG) и `exportChart.ts` в `ui/src/charts/striplog/`. Окно приложения, не браузерное. Команда `holes.data_window` (uiOnly), для Claude — `chart.striplog` |
| Экспорт | SVG — сериализация со встроенными шрифтами Montserrat и Inter (`@font-face` как data URL, ADR 0006). PNG — та же SVG через `Image` → `canvas` (×2). CSV — чистая функция: на каждую скважину объединяются границы всех колонок, строки `Скважина;От;До;<колонки…>`, пустое остаётся пустым. Запись — новый мост `saveFile(name, kind, data)`: `kind` — png, svg, csv или bfstyle; данные — строка или байты; свои фильтры диалога; BOM только для CSV |

## Варианты

| Вопрос | Варианты | Выбор и причина |
|--------|----------|-----------------|
| Передача стволов | А) JSON по набору (как в BF); Б) BFA1 частями: точки f4 от начала части, интервалы — глубины и значения, размещение в Worker; В) ядро отдаёт xyz концов каждого интервала (f8) | **Б.** 50 тыс. стволов — примерно 20–30 МБ вместо ~150 МБ JSON, без округления до 1 см (BF нарушал 5.4). В — 5 млн × 48 Б = 240 МБ на каждое поле и пересчёт при смене поля. Расчёт дуги на клиенте по станциям и направлениям отвергнут: он дублирует на TS 5 методов десуртинга |
| Стили и отображения | А) всё в `settings`; Б) таблица `styles`, отображения — `objects(chart)` + `charts` (миграция 0004); В) стили объектами дерева | **Б.** Совпадает с ADR 0003. `settings` — это настройки вида, они необязательны в `.bfggis`. В засоряет дерево, а `object_refs` с RESTRICT противоречит правилу «удаление стиля оставляет копию» |
| Ключи настроек вида | А) один JSON `view`; Б) ключ на тему; В) строка на элемент (`hidden:set:3`) | **Б.** Меньше конфликтов и объём записи, лимит проверяется внутри одного значения. В — тысячи строк, лимит 2000 трудно удерживать |
| Отсечение | А) `renderer.clippingPlanes` для всей сцены (как в BF); Б) общий массив плоскостей у отсекаемых материалов | **Б.** Подложка, линия разреза и гизмо остаются видимыми без обходных приёмов |
| Замер кадра | А) не мерить; Б) мс программного рендера как бюджет; В) бюджет на детерминированные счётчики, мс — в отчёт | **В.** Мс под SwiftShader шумят, а счётчики ловят рост числа вызовов отрисовки |
