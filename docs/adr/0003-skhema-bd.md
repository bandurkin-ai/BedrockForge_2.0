# ADR 0003. Схема БД на двух диалектах: SQLite и PostgreSQL 16

**Статус:** Принято, 2026-11-16 (Э0). Состав таблиц этапов Э3+ уточняется миграциями своих этапов; принципы — обязательны с Э2.

## Контекст

- ТЗ 6.5 (правила хранения), 6.6 (версии, 409), 6.11 (сервер), 7.3–7.4, 7.6, 7.10, 10.1, 17.3. Приложение Е: `models.py` BF (20 таблиц PostgreSQL, JSONB, `func.now()`) — основа, переписать на переносимые типы.
- Проверено в облаке (SQLAlchemy 2.0.57): `sa.Uuid` даёт `CHAR(32)` на SQLite и `UUID` на PostgreSQL; `JSON().with_variant(JSONB, "postgresql")` даёт `JSON` / `JSONB`; диалект `postgresql+pg8000` загружается. Сделан замер трёх схем хранения интервальных таблиц (п. 4).

## Решение

### 1. Два уровня данных

| Уровень | Desktop (SQLite) | Сервер Э25 (PostgreSQL 16) | Таблицы |
|---------|------------------|----------------------------|---------|
| Проект | Файл `project.sqlite` в папке проекта | Отдельная схема `p_<id>` одной базы (`schema_translate_map`) | Все таблицы п. 3 — одинаковые |
| Экземпляр | `instance.sqlite` в профиле | Схема `public` | `jobs`, `job_log` (без проекта); на Э25 — `projects`, `users`, `sessions`, `project_members`, `object_locks`, `audit_journal`, `uploads` |

В таблицах проекта **нет `project_id`**: проекты изолированы физически; удаление проекта — удаление папки или `DROP SCHEMA`; импорт `.bfggis` — новый файл (переименование в конце) или новая схема в одной транзакции (DDL в PostgreSQL транзакционен).

### 2. Переносимые типы (объявляются в `core/bf_core/db/dialect.py`)

| Назначение | Тип SQLAlchemy | SQLite / PostgreSQL | Правило |
|------------|----------------|---------------------|---------|
| Ключ строки | `BigInteger().with_variant(Integer, "sqlite")` | `INTEGER PRIMARY KEY` / `BIGINT` identity | `BigInteger`-ключ в SQLite не автоинкрементируется — только через вариант |
| Внешний идентификатор (uid проекта, сессии, загрузки) | `sa.Uuid` | `CHAR(32)` / `UUID` | Не `CHAR(36)`; ключом строк не служит. При импорте `.bfggis` все id создаются заново |
| JSON | `sa.JSON().with_variant(JSONB, "postgresql")` | `JSON` (текст) / `JSONB` | Запросы внутрь JSON — только через помощники `dialect.py`; поля для фильтра и сортировки выносятся в колонки; у каждого JSON-поля — модель pydantic |
| Время | `UtcDateTime` (свой `TypeDecorator`) | `DATETIME` без зоны / `TIMESTAMPTZ` | Всегда UTC; значение ставит приложение (`server_default now()` не используется) |
| Число | `sa.Double` | `REAL` / `DOUBLE PRECISION` | float64; пропуск — `NULL`, не ноль |
| Двоичные данные | `sa.LargeBinary` | `BLOB` / `BYTEA` | Только малые (векторы строк); массивы — в blobs |
| Перечисление | `sa.String(n)` | — | Проверка в pydantic; без `CHECK` и native enum — миграции проще |
| Название | `name` + `name_key` | — | `name_key` = NFC + `casefold()`; уникальность и поиск — по нему (`NOCASE` и `LIKE` SQLite не знают кириллицу) |

### 4. Интервальные таблицы до 5 млн строк

- `dh_rows` — одна строка на интервал. `hole_id` — целое из `dh_holes`. Все числовые колонки таблицы лежат одним вектором float64 little-endian в `num`: позиция = `dh_columns.slot`, пропуск = NaN, короткий вектор = пропуски в хвосте (новая колонка добавляется без переписывания строк). `qual` — признак значения на слот (ниже или выше предела обнаружения, код пропуска), `NULL`, если все обычные. Текстовые значения — `txt` (JSON).
- Интерфейс, API и `.bfggis` по-прежнему работают со значениями по имени компонента (7.10); упаковка — внутреннее дело слоя БД.
- Индекс ТЗ `(set_id, hole_id, from_m)` реализован как `(table_id, hole_id, from_m)`: таблица принадлежит одному набору, `hole_id` уникален в наборе.
- Сортировка, фильтр и статистика больших таблиц — по колоночному снимку `cache\tables\<table_id>-<rev>.parquet` (DuckDB, Arrow; `np.frombuffer` → Arrow без копии); `rev` растёт при каждой правке.

Замер: 1 млн строк × 10 числовых колонок, SQLite 3.53.1, Python 3.12.16, облако (4 ядра):

| Вариант | Запись + индекс | Чтение в numpy | Статистика колонки | Страница сортировки | Размер |
|---------|-----------------|----------------|--------------------|---------------------|--------|
| A. JSON по имени (как в BF) | 9,3 с | 5,9 с | 0,93 с (SQL) | 2,7 с (SQL) | 307 МБ |
| **E. Вектор float64 (принято)** | 2,0 с | 1,4 с | 0,02 с (numpy) | 0,13 с (numpy) | 114 МБ |
| B. Физическая таблица на каждую таблицу набора | 2,9 с | 2,3 с | 0,09 с (SQL) | 1,9 с (SQL) | 116 МБ |

На 5 млн строк: A — чтение ≈ 30 с и 1,5 ГБ (не укладывается в «аудит ≤ 30 с»); E — запись ≈ 10 с, чтение ≈ 7 с, 0,6 ГБ; B требует DDL во время работы вне Alembic на двух диалектах.

### 5. Версии и 409

- `objects.version`, `styles`, `settings`, `dh_tables.rev` — `version_id_col` SQLAlchemy: `UPDATE … WHERE id = :id AND version = :v`; 0 строк → 409 `{code: "version_conflict", message, hint}`. Запрос на изменение несёт `expected_version`, ответ — новую версию.
- Возврат к версии — новая версия; отмена правки — в одной транзакции с изменением данных, запись `edit_log` помечается `undone`.

### 6. Правила Alembic

| Правило | Значение |
|---------|----------|
| Цепочка | Одна линейная цепочка ревизий для обоих диалектов; ветвления по диалекту — только вызовами `dialect.py` |
| SQLite | `render_as_batch=True`; `naming_convention` для всех ограничений; миграция — одна транзакция; `PRAGMA foreign_keys=OFF` на время batch и `foreign_key_check` после |
| Обратимость | У каждой ревизии `downgrade`; тест `upgrade head → downgrade base → upgrade head` и сравнение с моделями (`compare_metadata` пусто) на SQLite и PostgreSQL 16; плюс миграция копии проекта предыдущего выпуска |
| При открытии | Проект старее — копия `backups\pre-migrate-<rev>.sqlite`, затем обновление; новее — отказ «обновите программу» |
| Сервер | Миграции — циклом по схемам проектов (`version_table_schema`) |
| `dialect.py` | Единственное место диалект-зависимого кода: типы-варианты, `PRAGMA`, `BEGIN IMMEDIATE`, upsert, захват задания, доступ к JSON, массовая вставка / `COPY`, advisory lock. Проверка CI: `sqlalchemy.dialects`, `PRAGMA`, `json_extract`, `->>` вне `db/dialect.py` не встречаются |

### 7. Драйвер PostgreSQL

| Драйвер | Версия | Лицензия | Решение |
|---------|--------|----------|---------|
| **pg8000** | 1.31.6 | BSD-3-Clause | **Принят:** чистый Python (нет `libpq.dll` в сборке), синхронный, SCRAM-SHA-256, TLS; URL `postgresql+pg8000://` |
| asyncpg | 0.32.0 | Apache-2.0 | Нет: только asyncio, ядро синхронное |
| psycopg 3 | 3.3.9 | **LGPL-3.0-only** | Запрещён ТЗ 6.3 (в BF был `psycopg[binary]`) |
| psycopg2 | 2.9.13 | **LGPL с исключениями** | Запрещён ТЗ 6.3 |

## Причины

- «Проект = файл SQLite = схема PostgreSQL» даёт один набор моделей и миграций и исключает класс ошибок «забыли фильтр по проекту» на сервере.
- Целочисленные ключи компактнее UUID в индексах на 5 млн строк; уникальность между проектами не нужна — `.bfggis` пересоздаёт id.
- Вектор float64 — самое быстрое чтение в numpy / Arrow при неизменной схеме на обоих диалектах.
- Время, выставляемое приложением, одинаково на SQLite и PostgreSQL и подменяется в тестах.

## Последствия

- SQL-фильтр по значению компонента невозможен — только через снимок Parquet или numpy; снимок перестраивается после правок (фоном, для 5 млн строк — секунды).
- pg8000 медленнее C-драйверов; массовая загрузка на сервере — через `COPY` в `dialect.py`; замер — на Э25.
- Список проектов на desktop читает `project_meta` каждого проекта (кеш в `instance.sqlite`).
- Удаление колонки помечает слот `deleted`; уплотнение векторов — отдельной командой.

## Альтернативы

| Вариант | Почему нет |
|---------|-----------|
| `project_id` во всех таблицах (как в BF) | В desktop лишняя колонка; на сервере — риск утечки между проектами; удаление проекта — миллионы `DELETE` |
| JSON по имени компонента (A) | Не проходит по времени и памяти на 5 млн строк |
| Физические таблицы на каждую таблицу набора (B) | DDL во время работы, блокировки DDL на сервере, перенос и отмена сложнее |
| UUID как ключ строк | Больше индексы, медленнее вставка |
| **Предложение заказчику:** хранить интервалы одним колоночным блоком на скважину (50 тыс. строк вместо 5 млн) | Быстрее ещё на порядок, но расходится с текстом ТЗ 6.5 «с индексами `(set_id, hole_id, from_m)`»; вернуться, если замеры Э3–Э5 не уложатся в бюджет |
