# ADR 0005. Сборка, обновление, лицензия

**Статус:** Принято, 2026-11-16 (Э0) — сборка и CI (п. 1–4, 7). **Предварительно** — обновление и лицензия (п. 5–6): уточняются на Э24 отдельным ADR и `docs/LICENSING.md`.

## Контекст

- Решения заказчика №5 (portable `.exe` и установщик с автообновлением), №8 (лицензия Ed25519, привязка к ПК, пробный период 30 дней). ТЗ 5.6 (S3, S7, S8), 5.7, 6.3, 10.4, 16, 17.2.
- Проверено в облаке 2026-11-16 (Linux; сборку под Windows это не заменяет):

| Проверка | Результат |
|----------|-----------|
| Схема electron-builder 26.18.0 | Опция `electronFuses` есть (9 ключей) — отдельный `@electron/fuses` не нужен |
| Шаблон `portable.nsi` electron-builder | **При каждом запуске** удаляет папку, распаковывает всё приложение, после выхода снова удаляет |
| Шаблон установщика | Распаковка через `Nsis7z` (код 7-Zip, LGPL) |
| Playwright `_electron` и предохранители | С `EnableNodeCliInspectArguments = false` Playwright не подключается (тайм-аут); с `true` — работает, даже при `RunAsNode = false` |
| numba 0.68.1, `cache=True` | Кеш пишется в `NUMBA_CACHE_DIR` с кириллицей и пробелом: в обычном Python и в сборке `onedir` каркаса Э0 на Linux со своим локатором (1,68 с → 0,24 с при втором запуске) |
| Nuitka на PyPI | Версии ≥ 4.0 — **AGPLv3+**; 2.8.10 — последняя под Apache-2.0 |
| Размер | Колёса ядра для Windows ≈ 223 МБ; `onedir` каркаса Э0 на Linux — 653 МБ (без ortools, pyproj, ezdxf); Electron ≈ 275 МБ после распаковки |

## Решение

### 1. Ядро `bf-core.exe`

| Тема | Решение |
|------|---------|
| Упаковка | PyInstaller 6.22.3, `onedir`, **без UPX**, spec-файл `core/bf-core.spec`; результат — `bf-core\bf-core.exe` + `_internal\` |
| Консоль | `console=True` (нужен stdout для `BF-READY`); оболочка запускает с `windowsHide`; режим UTF-8 (`X utf8`) |
| Процессы | `multiprocessing.freeze_support()` первой строкой точки входа; исполнители — тот же `bf-core.exe` |
| Импорты | Явный список в spec: диалекты SQLAlchemy (`sqlite`, `postgresql.pg8000`), `pythoncdt._core`, обработчики заданий; uvicorn запускается программно (без строковых импортов); миграции Alembic, данные pyproj и ezdxf — как файлы данных |
| Исключения | tkinter, тесты, группа `dev` (matplotlib, GeostatsPy не попадают) |
| Кеш numba | `NUMBA_CACHE_DIR = %LOCALAPPDATA%\BedrockForge\cache\numba\<версия ядра>` — задают оболочка и само ядро до импорта numba. В `onedir` файла исходника на диске нет, и штатный локатор numba эту папку не использует — ядро регистрирует свой локатор кеша (`bf_core/numba_cache.py`, метка свежести — exe); запасной вариант — собирать модули с ядрами numba как `.py` (`module_collection_mode = "py"`). Прогрев — фоновым заданием при первом запуске |
| Самопроверка | `bf-core.exe --selftest`: импорт всех тяжёлых библиотек и мини-расчёты (дымовой скрипт ADR 0001), отчёт JSON, код возврата 0 |

### 2. Оболочка (electron-builder 26.18.0)

| Тема | Решение |
|------|---------|
| Цели | `nsis` — установщик «для текущего пользователя»; portable — п. 3; только x64 |
| NSIS | `oneClick: false`, `perMachine: false`, `allowElevation: false`, выбор папки, русский язык, ассоциации `.bfggis` и `.bfproj` в HKCU; права администратора не нужны |
| asar | `asar: true`: бандлы main и preload (esbuild) и `ui/dist`; `node_modules` в asar не кладётся. Интерфейс отдаётся по `app://bedrockforge` из asar — покрыт проверкой целостности (перенос `ui/dist` из `extraResources` в asar — не позже Э24) |
| `extraResources` | `core/dist/bf-core/` → `resources\bf-core\` (исполняемые файлы не могут лежать в asar). Список SHA-256 файлов ядра — внутри asar; при старте сверяется `bf-core.exe`, полностью — фоном (Э24) |
| Предохранители | Через `electronFuses`: `runAsNode: false`, `enableNodeOptionsEnvironmentVariable: false`, `enableNodeCliInspectArguments: false`, `onlyLoadAppFromAsar: true`, `enableEmbeddedAsarIntegrityValidation: true`, `enableCookieEncryption: true`, `grantFileProtocolExtraPrivileges: false` |
| Два профиля | `release` — все предохранители; `e2e` — то же, но `enableNodeCliInspectArguments: true`. Дымовой E2E идёт на `e2e`; артефакт `release` проверяется `BedrockForge.exe --selftest` (запуск, ядро отвечает, версии совпадают, кадр 3D, код возврата). До Э24 собирается только `e2e` |
| Подпись | При наличии секретов сертификата; без него — предупреждение SmartScreen и честная инструкция в README |

### 3. Portable

- Стандартная цель `portable` распаковывает приложение при каждом запуске. С ядром (≈ 0,7 ГБ, тысячи файлов) это десятки секунд — бюджет «запуск ≤ 6 с» недостижим; двойной щелчок по `.bfggis` при открытой программе вызвал бы вторую полную распаковку.
- **Решение:** `BedrockForge-x.y.z-portable.exe` собирается своим NSIS-скриптом `tools/portable.nsi` из папки `win-unpacked`. Первый запуск: распаковка в `<папка exe>\BedrockForge-x.y.z\` (нет права записи — в `%LOCALAPPDATA%\BedrockForge\portable\x.y.z\`), создание флага `BedrockForge.portable`, запуск. Следующие запуски: сверка маркера версии и немедленный запуск уже распакованного. Один `.exe`, без установки и прав администратора — решение №5 соблюдено.
- До готовности скрипта (Э1) используется стандартная цель; время запуска измеряется в `windows.yml`.
- Первый запуск показывает окно «Подготовка к первому запуску…» — отступление от «одной заставки», согласовать с заказчиком на В1.

### 5. Обновление — предварительно

| Тема | Решение |
|------|---------|
| Механизм | electron-updater 6.8.11, только для установленной версии (NSIS). Portable показывает «Доступна версия x.y.z» со ссылкой |
| Источник | Приватный репозиторий без токена не работает; токен в приложение не кладём. Провайдер `generic` с адресом из конфигурации. Вариант А — публичный репозиторий только с выпусками `BedrockForge2-releases` (`…/releases/latest/download/`); вариант Б — свой HTTPS-сервер. Выбор — Э24; смена адреса не требует смены логики |
| Проверка | HTTPS, SHA-512 из `latest.yml`, подпись издателя при наличии сертификата (S7). **Предложение:** подписывать `latest.yml` отдельным ключом Ed25519 и проверять в main до установки — защита при взломе хостинга, пока нет сертификата |
| Поведение | Проверка при запуске и по команде, только при наличии сети, без сообщений об ошибке в офлайне; загрузка фоном; установка — по согласию пользователя после остановки ядра (незавершённые задания вернутся в очередь) |

### 6. Лицензия — предварительно

| Тема | Решение |
|------|---------|
| Файл `license.bflic` | JSON `{format: "bflic/1", kid, payload, signature}`; `payload` — base64 от UTF-8 JSON `{id, customer, hwid, features[], issued, expires, version_max}`; `signature` — Ed25519 по байтам `payload`. Подписываются байты, а не «канонический JSON» — проверка одинакова в Python и Node |
| Ключи | Открытый — в ядре (`cryptography`) и в оболочке (`crypto.verify`); закрытый — только у заказчика, в репозитории его нет; `kid` позволяет сменить ключ |
| Код ПК (HWID) | `MachineGuid`, серийный номер системного тома, идентификатор процессора; каждый компонент хешируется SHA-256 отдельно, код ПК — три усечённых хеша; лицензия действительна при совпадении ≥ 2 из 3. Считает ядро (`winreg`, `ctypes`) — без WMI и дочерних процессов |
| Пробный период | 30 дней с первого запуска; отметки в HKCU, `%APPDATA%`, `%LOCALAPPDATA%` с HMAC; берётся самая ранняя дата первого запуска и самая поздняя отметка «последний запуск»; часы раньше неё → пробный период приостановлен с сообщением |
| «Только просмотр» | Ядро отклоняет изменяющие запросы и экспорт (403 `license_readonly`); интерфейс показывает причину недоступности команд; данные не блокируются и не удаляются |
| На Э1 | Окно «Лицензия»: код ПК и пробный срок; полная схема отметок и защита — Э24 |
| Защита кода | Лицензионный модуль ядра — **Cython** в `.pyd` (Nuitka ≥ 4.0 исключена лицензией AGPL); оболочка — asar, предохранители, обфускация модуля лицензии. Оговорка в `LICENSING.md`: защита повышает стоимость обхода, но не исключает его |

### 7. SBOM и уведомления о лицензиях

CycloneDX в каждом выпуске: `cyclonedx-py environment` для ядра, `cyclonedx-npm --omit dev` для `app` и `ui` → три файла `sbom-*.cdx.json`; в дистрибутив кладутся `THIRD_PARTY_NOTICES.txt` и `LICENSES.chromium.html`.

## Причины

- `onedir` без UPX — меньше ложных срабатываний антивируса и нет распаковки ядра при каждом запуске (17.2.7).
- Ядро вне asar запускается как обычный exe; интерфейс внутри asar защищён проверкой целостности.
- Два профиля предохранителей — единственный способ совместить E2E на собранном `.exe` (ТЗ 10.4) и защиту (ТЗ 5.7): конфликт воспроизведён.
- Подпись по байтам `payload` снимает расхождения сериализации JSON между Python и JavaScript.

## Последствия

- Проверяемый Playwright exe отличается от выпускаемого одним предохранителем; выпускаемый проверяется только самопроверкой.
- Свой локатор кеша numba опирается на внутренние классы numba (`_CacheImpl`, `_UserProvidedCacheLocator`) — при обновлении numba проверяется самопроверкой; запасной вариант оставляет исходники ядер на диске открыто.
- Свой `portable.nsi` — код, который нужно сопровождать и тестировать (первый запуск, повторный, нет прав записи, обновление версии).
- Обновление portable — вручную; автообновление — только у установленной версии.
- Без сертификата подписи SmartScreen предупреждает при первом запуске.
- Распакованное приложение ≈ 1 ГБ; установщик со сжатием LZMA оценочно 330–370 МБ при лимите 400 МБ — размер проверяется на каждом PR.

## Альтернативы

| Вариант | Почему нет |
|---------|-----------|
| PyInstaller `onefile` | Распаковка сотен МБ во временную папку при каждом старте, срабатывания антивируса |
| Nuitka для ядра или модуля лицензии | 4.x — AGPLv3+; 2.8.10 (Apache-2.0) больше не развивается |
| Стандартная цель `portable` навсегда | Не проходит бюджет запуска |
| Portable как `.zip` | Проще и быстрее, но решение №5 требует `.exe`; **предложение заказчику** — выкладывать zip дополнительно |
| Один профиль предохранителей без E2E на exe | Нарушает ТЗ 10.4 |
| Обновление через GitHub API с токеном | Токен в клиенте извлекается |
| `useZip` вместо `Nsis7z` | Убирает LGPL-плагин из установщика, но отключает разностные обновления и увеличивает размер; решить на Э24 |
