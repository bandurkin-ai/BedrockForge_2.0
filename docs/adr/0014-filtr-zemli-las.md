# ADR 0014. Фильтр «земли»: облака точек LAS/XYZ, классификация, ЦТМ из облака (Э7.1, Д-22)

**Статус:** Принят 2026-11-19 (проект — architect, fable / xhigh; принял оркестратор: решения 1–4 «на подтверждение» приняты как предложены; владелец 2026-11-19: RGB и интенсивность не нужны). Не пересматриваются: ADR 0001 (зависимости только через ADR), 0002 (задания, `spawn`, blobs), 0003 (схема), 0004 (части, LOD, бюджеты 3D), 0007 (BFA1, ETag), 0011 (слой точек — `line_layer` с `points_only`; «Построить ЦТМ» — `geo/dtm.py`, задание `model.dtm`), 0012 (Д-22: атрибуция, LAZ не нужен, приёмка на синтетике).

## Контекст

- ТЗ 7.35 Д-22 (импорт LAS 1.2–1.4 и XYZ, шум, CSF с доработками для карьера, ЦТМ из земли, команды, Т-З1…Т-З4, замер: 10 млн ≤ 90 с и ≤ 4 ГБ на 4 ядрах, 50 млн — по частям ≤ 6 мин), 7.35.4 (команды и лента), 7.35.5 (laspy / lazrs не берём), 7.35.8 (№ 13 — приёмка на синтетике, № 14 — LAZ не нужен), 7.20, 9.12 (потоково, прогресс, отмена, негативные тесты).
- Есть (Э7, Э8): слой точек (`formats/lineset.py`, `lines/store.py`: blobs `xyz <f8`, `seq <u4`, `attrs` Parquet), читатель XYZ/CSV/TXT/DAT `formats/points.py::read_points` (табличные читатели Э3, таблица целиком в памяти, все лишние колонки — атрибуты), показ `viz/lines.py` + `ui/src/viz/lines/*` (части ≤ 256 тыс. точек, уровни 0 / 4 / 32 м, выбор на CPU), «Построить ЦТМ» (`geo/dtm.py`, `wireframes/jobs.py`; 1 млн точек — 8,1–8,6 с, пик 660 МБ). В стеке: numpy, numba, scipy 1.18.1, pyarrow 25.0.1, PythonCDT.
- Нет: LAS, шума, фильтра, команд, класса у точки. В ядре нет ни одного ядра numba с `prange` / `parallel=True` — параллельного кода до Э7.1 не было.
- **Главная находка: основа Э7 не держит 10–50 млн точек** (оценка по коду; первым замером 7.1.3 подтверждается):

| Место | Что происходит на 50 млн (10 млн) | Следствие |
|---|---|---|
| `LineSet` + `_clean_table` | Облако целиком в памяти; любая числовая колонка атрибутов приводится к float64 — `class` стоил бы 8 байт на точку; Parquet пишется через `BytesIO` | Импорт — несколько ГБ; класс нельзя заменить, не переписав таблицу |
| `LayerFiles.array` | `np.fromfile` читает blob целиком | Любой читатель держит 1,2 ГБ (0,24) |
| `viz/lines.py::build` | В **процессе API**: чтение `xyz`, `argsort` кода Мортона, копия `pts[order]`; раскладка остаётся в кеше | Пик ≈ 3,2 ГБ (0,64), постоянно ≈ 1,6 ГБ (0,32), секунды без ответа ядра — тот же дефект, что долг Э9 по LOD каркасов |
| Уровни точек 0 / 4 / 32 м | Уровень 1 — одна точка на ячейку 4 м: облако 20 точек/м² редеет в 300 раз за один шаг | Либо всё облако на видеокарте (650 МБ), либо «пустой» кадр |
| `model.dtm` | 600 байт и 8 мкс на точку; 7 млн точек земли → ≈ 4 ГБ, > 60 с, каркас 14 млн треугольников; совпадение в плане с разным Z — отказ | ЦТМ из облака без прореживания не строится |

## Варианты

| Вопрос | Варианты | Выбор и причина |
|---|---|---|
| Хранение 10–50 млн точек | А) слой точек Э7 как есть; Б) тот же `line_layer` (`points_only`) с признаком `meta.cloud`: пространственный порядок хранения, вложенные уровни, столбцы — сырые blobs по ролям, чтение срезами; В) новый вид объекта с октодеревом (Potree / COPC) | **Б.** Буква Д-22 («облако — слой раздела „Линии“, при нехватке — слой плитками»); без миграции и нового раздела дерева; класс — 1 байт, заменяется отдельным blob. А не проходит по таблице выше. В — новый объект, дерево, архив, свой обход в окне: не на 2 окна |
| Уровни показа | А) прореживание части по запросу (Э7); Б) вложенные уровни как **префиксы части** (0; 0,5; 2; 8; 32 м), считаются один раз при импорте; В) аддитивное октодерево | **Б.** Ответ ядра — срез файла (без раскладки в памяти API), протокол `parts/{k}?lod=` и `linesSource` не меняются (шаги уровней интерфейс уже берёт из манифеста). В — после реальных облаков, если кадр не уложится |
| LAS | А) laspy (BSD-2); Б) свой читатель: структурный dtype numpy + `memmap` порциями | **Б** (7.35.5): формат — заголовок и записи фиксированной длины, зависимость не нужна |
| Запись LAS | А) нет (только CSV); Б) только новый файл; В) новый файл + «по исходнику» (копия исходного LAS с заменой класса) | **В.** Д-22 требует «экспорт в LAS с классом»; «по исходнику» сохраняет цвет, время GPS, VLR и СК байт в байт ценой ~40 строк; писатель новых файлов нужен и тестам (laspy нет) |
| Алгоритм земли | А) классический CSF: шаги по времени + подгонка склонов; Б) CSF как задача с препятствием + рост по склону + грани (Д-22); В) PTD (Axelsson), морфологические PMF / SMRF | **Б.** А не оседает в яму 300 м за разумное число шагов и теряет бровки; В принимают уступ за здание и последовательны |
| Положение покоя ткани | А) шаги по времени; Б) активное множество + прямой решатель SuperLU (`scipy.sparse`); В) система равновесия на сетке ткани с односторонним ограничением: каскад сеток, красно-чёрная релаксация с проекцией | **В.** Система та же, что в Б (разрежённая, 5 точек), шагов по времени нет — глубина ямы не влияет; ядро ~80 строк numba, параллельно и побитно детерминировано, память O(частиц). Б — последовательный, заполнение множителей на 2 млн частиц, результат зависит от потоков BLAS; остаётся **эталоном в тесте** (≤ 1e−6 м на малой сетке) |
| Параллельность и Т-З4 | А) numba `prange` (`parallel=True`); Б) потоки Python (`ThreadPoolExecutor`) над ядрами `nogil=True` по **фиксированным полосам** данных; В) процессы | **Б.** Границы полос не зависят от числа потоков, полосы пишут в непересекающиеся срезы, свёртки — только `min`/`max` и целые счётчики → побитно при 1/2/4/8. А тянет выбор threading layer в `.exe` (workqueue не потокобезопасен) и первый `parallel=True` в проекте; В — копии облака |
| ЦТМ из 10 млн точек | А) все точки земли в `build_dtm`; Б) прореживание земли по ячейке плана до ≤ 2 млн вершин, затем `build_dtm` как есть; В) триангуляция плитками со сшивкой | **Б.** `build_dtm` не меняется (вершины — исходные точки побитно), 2 млн — 17 с и 1,3 ГБ; В — швы и новый код триангуляции |

## Решение

### 1. Хранение облака (`lines/cloud.py`, `lines/cloud_build.py`, `geo/cloud_kernels.py`; миграции нет)

| Что | Решение |
|---|---|
| Объект | `objects(kind="line_file")` → один `line_layer` (`points_only`, `line_count = 0`) с `objects.meta.cloud`; `cloud_id` команд = id слоя. Обычный слой точек Э7 (≤ 2 млн, с атрибутами и текстом) остаётся как был; при > 2 млн точек через «Импорт файлов» — предупреждение «загрузите как облако» |
| Blobs (владелец `object`; новые роли в `BLOB_ROLES`) | `xyz <f8 N×3` (24 Б/точку), `seq <u4` (номер записи исходника), `class u1` (код ASPRS 0–255), `ret u1` (младшие 4 бита — номер возврата, старшие — число возвратов); после фильтра — `h <f4` (высота над землёй по нормали, м; NaN — нет); после ЦТМ — `dz <f4` (Z − ЦТМ, м). Итого 30 Б/точку: 10 млн — 0,3 ГБ, 50 млн — 1,5 ГБ; исходный файл — blob `source` (правило 6.7) |
| Порядок хранения | Плитки 64 м в порядке Мортона, внутри — код Мортона ячеек 1 м; **части** — отрезки подряд идущих точек ≤ 524 288 (уточняется замером 7.1.3); внутри части точки переставлены по рангу уровня: сначала представители ячеек 32 м, затем 8, 2, 0,5 м, затем остальные (ячейки X, Y, Z сетки проекта, представитель — первая точка в порядке хранения, уровни вложены). Уровень `lod` части = её первые `n_lod` точек |
| `meta.cloud` | `{format: 1, levels: [0, 0.5, 2, 8, 32], parts: [{start, n: [n0…n4], bbox, origin}], bbox, classes: {код: число}, source: {kind: "las"\|"xyz", every}, ground: {params, counts, algo, at} \| null, dz: {wireframe_id, name} \| null}`; сведения LAS — `meta.source.las` (версия, формат точек, длина записи, scale, offset, WKT ≤ 32 КБ, ключи GeoTIFF, список VLR) |
| Сборка при импорте | Два прохода по источнику порциями 1 млн записей: счёт точек по плиткам → раскладка подсчётом во временный файл (`memmap`) → части по одной (сортировка, ранги уровней) → потоковая запись blobs с SHA-256. Память задания ≤ 1 ГБ при любом N; отмена не оставляет файлов |
| Чтение | `open_cloud()` — срезы с диска (`np.fromfile(offset, count)` / `memmap` на время задания; на Windows отображение не держится дольше запроса — риск ADR 0013). `read_layer` (LineSet целиком) для облака не вызывается: три места вызова (`viz`, `model.dtm`, `export.lines`) ветвятся по `meta.cloud` |
| Замена классов | Новые blobs `class`, `h` (blobs неизменяемы), `objects.version + 1`, `meta.cloud.classes / ground`, событие `objects.changed`; `xyz`, `seq` и уровни не трогаются. Проверка версии при записи: облако изменилось за время задания → `cloud_changed` |
| Атрибуты точки | `attr_schema`: «Класс», «Возврат», «Число возвратов», «Высота над землёй, м», «Отклонение от ЦТМ, м» с пометкой `store` (роль blob); `GET /lines/layers/{id}/attrs` для облака читает срезы blobs |

### 2. Показ в 3D и выбор (`viz/cloud.py`; `ui/src/viz/lines/*`, `modules/scene/linesSource.ts`)

| Что | Решение |
|---|---|
| Ядро | Те же адреса: `GET /viz/lines/{id}` (манифест из `meta.cloud`: части, 5 уровней) и `/parts/{k}?lod=&color=`: срез `xyz[start : start + n_lod]` − начало части → `f4`; `line u4` (номер точки — строка атрибутов); `value u1` — код класса либо квантованное значение режима (`h`, `dz`: шаг 0,02 м, ±2,5 м, 255 — пусто). Память процесса API — одна часть (≤ 13 МБ), раскладка не строится и не кешируется; ETag — ключ ADR 0007 + SHA blob режима |
| Отрисовка | `THREE.Points` 2 px без каймы (обычный слой точек — 5 px с каймой, без изменений); цвет — палитра 256×1 (текстура) по `value`; режимы «Класс» (по умолчанию, если классы есть), «Цвет слоя», «Высота над землёй», «Отклонение от ЦТМ»; видимость класса — альфа палитры (скрытые не рисуются и не выбираются); общие `clipPlanes` |
| Уровень и бюджеты | Уровень — шаг прореживания на экране ≤ 2 px, гистерезис 20 %; видеопамять — доля линий 25 % (`LINES_SHARE`), 13 Б/точку; новый бюджет точек кадра `POINT_BUDGET`: встроенная 6 млн, дискретная 20 млн, программная 1 млн (правило `applyTriangleBudget`: сначала грубеют мелкие на экране части); помета «упрощено» |
| Выбор щелчком | Как у слоя точек Э7: ближайшая точка ≤ 8 px на CPU по показанным частям у курсора (отбор по габариту части на экране); цель ≤ 50 мс (5.3) — замер в `perf3d`; запасной путь — экранная сетка уровня в Worker. «Свойства»: X, Y, Z (float64 из ядра), класс, возврат, `h`, `dz` |

### 3. Форматы (`core/bf_core/formats/`; правила 9.12)

| Формат | Решение |
|---|---|
| LAS, чтение (`las.py`) | Заголовок 1.2 (227 Б), 1.3 (235), 1.4 (375: 64-битные счётчики, EVLR); форматы точек 0–10 (20, 28, 26, 34, 57, 63, 30, 36, 38, 59, 67 Б) + «лишние байты» по длине записи; структурный dtype, `np.memmap`, порции 1 млн записей; **X, Y, Z = int32 · scale + offset в float64**; класс — 5 бит (форматы 0–5) или байт 0–255 (6–10, extended classification); возврат и число возвратов — 3+3 или 4+4 бита; признаки withheld / overlap считаются → предупреждение. Не читаются (в составе — «не загружается»): интенсивность, RGB / NIR, время GPS, угол, user data, source id, волновые пакеты |
| СК в LAS | VLR и EVLR `LASF_Projection`: 2112 (WKT), 34735–34737 (ключи GeoTIFF) — сохраняются в `meta.source.las` как метаданные, без перепроецирования; метка `objects.crs` — через `crs.py` (EPSG из ключей 3072 / 2048 или имя из WKT); координаты в градусах — предупреждение «фильтр считает в метрах» |
| Проверки | Подпись `LASF`; версия (1.0 — отказ, 1.1 читается как 1.2 с предупреждением); длина записи ≥ длины формата; scale конечен и ≠ 0; число записей заголовка против размера файла (обрезанный — целые записи + предупреждение); пустой файл; > 50 млн точек — мастер предлагает «каждая k-я запись», > 200 млн после прореживания — отказ `too_many_points`; прогресс и отмена между порциями |
| LAZ | `.laz`, бит 7 формата точек или VLR `laszip encoded` → `{code: "laz_not_supported", message: "Сжатые облака LAZ не читаются.", hint: "Сохраните облако как LAS без сжатия (CloudCompare: «Сохранить как» → LAS; LAStools: laszip -i облако.laz -o облако.las) и загрузите снова."}` |
| LAS, запись (`las_write.py`) | (а) **по исходнику** (облако из LAS, по умолчанию): копия blob `source`, в записях по `seq` заменяются только биты класса — остальное байт в байт; (б) **новый файл** (облако из XYZ или по выбору): LAS 1.2 формат 0, при кодах > 31 — 1.4 формат 6; scale 0,001 (или исходный), offset — целое начало; порядок хранения. Писатель знает форматы 0–10 (доп. поля нулями) — им строятся тестовые файлы. Цикл: целые X, Y, Z совпадают, координаты — в пределах 1 масштаба |
| XYZ / CSV / TXT | Читатель Э7 остаётся для обычных слоёв точек. Облако — `points_stream.py`: разделитель, кодировка, десятичный знак и колонки — по голове файла (разбор Э7), тело — потоком `pyarrow.csv.open_csv` (в стеке) во временные столбцы; колонки X, Y, Z, «класс» (необязательно); остальные не грузятся (предупреждение); пустой Z — точка пропускается и считается |
| CSV, запись | `X;Y;Z;класс[;h]`, числа `repr`, порциями, порядок хранения |

### 4. Фильтр земли (`geo/ground.py` — конвейер, блоки, потоки; `geo/ground_kernels.py`, `ground_cloth.py`, `ground_grow.py` — numba `cache=True, nogil=True`, без `fastmath`)

Постановка — публикация Zhang et al. (2016); этапы 3–7 — своя реализация идей, перечисленных в Д-22 (образец — Incline Design, MIT); код Rust не читается для переноса.

| № | Этап | Что делает | Сложность, память, потоки |
|---|---|---|---|
| 1 | Индекс | Сортировка подсчётом точек по ячейкам плана `CR/2`; по ячейке — самый низкий возврат | O(N); 8 Б/точку; полосы |
| 2 | Шум | Точка без `k_min` соседей в радиусе `r_ш` (3D, ранний выход) → 7; шум не участвует дальше. В расчёт ткани идут минимумы ячеек — «сетка прореживания» Д-22 встроена, отдельного параметра нет | O(N·k); полосы |
| 3 | Препятствие | Для частицы ткани (шаг `CR`) — плоскость МНК по минимумам ячеек в радиусе 1,5·`CR`, её высота в частице (идея 2: не ближайшая точка); нет данных в 2·`CR` — частица вне системы | O(частиц); полосы |
| 4 | Ткань | Мембрана под нагрузкой с ограничением u ≤ препятствие: `u = min(h, (Σ соседей + p·CR²)/4)`; каскад сеток от ≤ 64×64 до `CR`, красно-чёрные проходы до изменения < 1e−4 м (идея 1: решается равновесие, не падение). `RI` задаёт ширину разрыва в данных W, в который ткань поднимается не выше 0,5 м: `RI` 1 / 2 / 3 → W = 8 / 16 / 32 м (`p = 4/W²`) | O(частиц), 40 Б/частицу; строки-полосы |
| 5 | Семена | Ячейки, чей минимум не выше ткани более чем на `CT` **по нормали к ткани** | O(ячеек) |
| 6 | Рост по склону (идея 3) | От семян по сетке минимумов: сосед принимается, если лежит ниже плоскости, продолженной от принятых ячеек 5×5 (спуск — любой крутизны: бровка, откос, подошва), либо выше неё не более `CT` при наклоне плоскости вверх ≤ α (вверх — только полого). Возвращает бровки, бермы и вершины, которые жёсткая ткань срезает | O(ячеек); последовательно в фиксированном порядке (≈ 1–2 с на 10 млн) |
| 7 | Грани (идея 4) | Не-земля на локально плоском участке круче 60° (PCA соседей): земля, если плоскость грани в пределах `R_б` в плане продолжается до точек земли и выше, и ниже (≤ `CT` от плоскости); фасад и крона этого не имеют | O(кандидатов·k); полосы |
| 8 | Классы | `h` — расстояние по нормали до поверхности земли (принятые минимумы, билинейно); `h ≤ CT` → 2; выше — 3 / 4 / 5 по порогам 0,5 / 2 м; ниже земли более `CT` и вне данных → 1; шум → 7 | O(N); полосы |

| Параметр | Диапазон (по умолчанию) | «Равнина» | «Карьер» (по умолчанию) |
|---|---|---|---|
| `cr`, м | 0,1–50 (1) | 1 | 1 |
| `ri` | 1–3 (2) | 3 | 2 |
| `ct`, м | 0,05–5 (0,5) | 0,5 | 0,5 |
| `r_b`, м | 1–20 (5) | грани выключены | 5 |
| `noise {r, k_min}` или `false` | 0,5–20 (2); 1–20 (3) | 2; 3 | 2; 3 |
| α (вверх), порог грани — константы профиля, предварительно | — | 30°; — | 55°; 60° |

- **Блоки («по частям»).** Сетка ткани делится на блоки 2048×2048 частиц с полем 64 м; классы получают точки ядра блока; пустые блоки пропускаются; точки читаются срезами частей. Облако 50 млн при 20 точках/м² — 1–4 блока. Память: свои массивы ≤ 12 Б/точку + сетки блока — 10 млн ≤ 1 ГБ, 50 млн ≤ 2,5 ГБ (бюджет 4 ГБ). Ожидаемое время 10 млн — 20–40 с при бюджете 90 с.
- **Потоки.** Число потоков — параметр задания (`min(8, ядер // исполнителей heavy)`); результат от него не зависит (вариант Б). Здания отдельно не выделяются (класс 6 не ставится): попадают в 3–5 по высоте — записано в руководстве.

### 5. ЦТМ из облака (`wireframes/cloud_source.py`; `wireframes/jobs.py`, `geo/dtm.py` — без изменения алгоритма)

| Что | Решение |
|---|---|
| Источник | `model.dtm` получает `clouds: [{layer_id, classes, cell?}]` рядом с `layer_ids`, `set_ids`; облако в `layer_ids` трактуется как `classes: null` (все, кроме 7). Остальное (граница, `max_edge`, «сразу в ЦТМ», `meta.built`) — как в Э7 |
| Прореживание | Одна точка на ячейку плана `cell`: по умолчанию `max(CR/2, √(площадь / 2 млн))` — не больше 2 млн вершин (журнал пишет шаг); представитель — точка с нижней медианой `h` (нет `h` — нижней медианой Z), при равенстве — меньший номер. Одна точка на ячейку исключает отказ «совпадают в плане с разным Z» на стенках; координаты вершин — исходные побитно |
| `terrain.from_points {cloud_id, classes: [2], l_max, boundary_id?, cell?}` | То же задание: `clouds: [{cloud_id, classes, cell}]`, `max_edge = l_max` (по умолчанию 5·`CR` последнего фильтра, иначе 5 м), `boundary: {layer_id: boundary_id}`. Нет точек класса → `no_ground` с подсказкой «запустите „Фильтр земли“» |
| Карта разностей | После построения: `dz` = Z − ЦТМ для всех точек (ядро `dtm_kernels.locate`), blob `dz`, `meta.cloud.dz`; журнал: СКО, P95 и наибольшее по модулю `dz` по земле; режим цвета «Отклонение от ЦТМ». Последний по приоритету подшаг |

## Последствия

- Слой точек получает второй вид хранения (`meta.cloud`); обычные слои точек Э7 не меняются. Редактор Э9 (`line_layer_versions`) облака не редактирует; отмена классификации до Э9 — повторный фильтр или импорт.
- Д-17 (Э11) получает писателей облака: LAS, CSV. Э9: изолинии и объём работают по ЦТМ из облака как по любому каркасу.
- Ядро получает образец параллельного детерминированного кода (полосы + `nogil`) — для Э16–Э19 (вариография, кригинг, RBF).
- Не входит: LAZ, RGB / интенсивность / время GPS как данные слоя, класс 6 «здание», ручная правка классов, обрезка облака по контуру, E57 / PLY / PTS, перепроецирование.
- В отчёт вехи: основа Э7 не держала 10–50 млн точек (таблица «Контекст»); приёмка Д-22 — на синтетике; константы профилей — предварительные.
