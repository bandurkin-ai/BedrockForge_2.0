# ADR 0004. 3D на встроенной графике

**Статус:** Принято, 2026-11-16 (Э0). Корректность проверяется в облаке под программным рендером; скорость на встроенной графике — заказчиком на вехах (в облаке GPU нет).

## Контекст

- Решение заказчика №12: ПК приёмки — Windows 11, 16 ГБ ОЗУ, встроенная графика (Intel Iris Xe / Radeon Vega; видеопамять делится с ОЗУ).
- ТЗ 5.3: вращение сцены «50 тыс. стволов + 10 млн треугольников» ≥ 20 кадров/с на встроенной графике; первое изображение каркаса 10 млн треугольников ≤ 3 с; клик ≤ 50 мс. ТЗ 5.4: ≤ 0,5 мм до 16 км. ТЗ 6.8, 7.13, 17.3.1, 17.4.8, 17.4.10.
- BF: сцена — монолит `scene3d.ts` (131 КБ); в BF2 делится на модули ≤ 600 строк (Приложение Е).
- Замер в облаке (Linux, 4 ядра, без GPU; Electron 45.2.3, three 0.170.0; 999 698 треугольников, 1280 × 800):

| Запуск | WebGL2 | Время кадра |
|--------|--------|-------------|
| Electron без ключей | **нет** (контекст не создаётся) | — |
| `--enable-unsafe-swiftshader` или `--use-angle=swiftshader` | да, SwiftShader | 0,8–0,9 с (≈ 1 кадр/с) |
| Через Playwright 1.65.0 без ключей | да (Playwright добавляет ключ сам) | 0,8–1,0 с |
| Через Playwright 1.49.1 (закреплён) без ключей / с ключами | **нет** / да | — / 0,9 с |

## Решение

### 1. Основа

| Тема | Решение |
|------|---------|
| API | WebGL2, three.js 0.170.0 (`WebGLRenderer`); WebGPU — не в v1 |
| Контекст | `powerPreference: "high-performance"`, ключ `force_high_performance_gpu` (как в BF): дискретная карта используется, если есть; `preserveDrawingBuffer: false` |
| Пакет | 3D — ленивый чанк (`import()` модуля `ui/src/viz`); основной пакет не содержит three. Логика (LOD, бюджеты, начала координат, отбор) — чистые модули без three, тестируются vitest в node |
| Отрисовка | Только по требованию: `invalidate()` → один `requestAnimationFrame`; непрерывно — лишь пока идёт вращение или анимация. Отбор по пирамиде видимости — на уровне частей; near/far пересчитываются каждый кадр |
| Снимок | Отдельный проход в буфер кадра (печать, E2E), без `preserveDrawingBuffer` |
| Сглаживание | Настройка: MSAA вкл/выкл, плотность пикселей 0,75–2; для встроенной графики по умолчанию MSAA выкл, плотность 1 |

### 2. Точность координат

| Правило | Значение |
|---------|----------|
| Начало объекта | Центр охвата, округлённый до целого метра (float64, хранится в `origin`); на видеокарту идёт `float32(координата − origin)` |
| Погрешность | Охват ≤ 16 км → модуль координаты ≤ 8000,5 м < 8192 м → шаг float32 = 2⁻¹¹ м ≈ 0,49 мм; ошибка округления ≤ 0,25 мм по оси, ≤ 0,43 мм в пространстве |
| Крупные объекты | Охват > 16 км по любой оси → части со своим началом (ячейки 8 км) |
| Начало сцены | Целочисленная точка у цели камеры; смещение части = `origin` части − начало сцены, считается в float64 на CPU; при уходе камеры дальше 4 км начало сцены переносится. Координаты UTM в буферы и матрицы не попадают |
| Граница ответственности | Расчёты, клик, сечения, измерения — float64 в ядре; буферы видеокарты и LOD — только показ, упрощённое помечается «упрощено» |

### 3. Геометрия, LOD и бюджеты

| Тема | Решение |
|------|---------|
| Каркасы | Части ≤ 64 тыс. треугольников (режет ядро); индексы `Uint16`, если вершин в части ≤ 65 536, иначе `Uint32`; нормали не передаются (`flatShading`) → 12–14 байт на треугольник: 10 млн ≈ 120–140 МБ на полном уровне |
| LOD | На каждую часть 3 уровня: 1, 1/8, 1/64 (pyfqmr в ядре, результат в `cache\`). Выбор по экранному размеру ограничивающей сферы, гистерезис 20 %. Первый показ — уровень 1/64 всего объекта (цель ≤ 3 с), далее догрузка по приоритету «ближе к центру экрана» |
| Бюджет треугольников в кадре | 8 млн — встроенная, 30 млн — дискретная, 1 млн — программный рендер; настраивается. При превышении понижается уровень самых мелких на экране частей, в строке состояния — «упрощено» |
| Класс графики | По строке `WEBGL_debug_renderer_info`: Intel / Iris / UHD / Vega / Radeon Graphics → встроенная; NVIDIA / Radeon RX / Arc → дискретная; SwiftShader / WARP / llvmpipe → программная (предупреждение). Переопределяется в «Настройке» |
| Память видеокарты | Менеджер бюджета ведёт учёт байт буферов и текстур: ≤ 1,5 ГБ на встроенной графике (4 ГБ на дискретной, настройка). Вытеснение по давности использования: сначала невидимые части, затем старшие уровни; уровень 1/64 не выгружается |
| Скважины | 50 тыс. стволов — объединённые отрезки частями по ~2 тыс. стволов (отбор по пирамиде); подписи — по масштабу и плотности на экране |
| Блочные модели | Только грани оболочки или среза (считает ядро); цвет — значение в атрибуте вершины + текстура легенды (смена легенды без перезагрузки геометрии); > 5 млн граней — объединение до родительских блоков, «упрощено» |

### 4. Данные, выбор, сбои

| Тема | Решение |
|------|---------|
| Передача массивов | `application/octet-stream`, little-endian, C-порядок; части запрашиваются по `Range`; `ETag` = SHA-256 blob (повтор → 304); одновременно ≤ 4 загрузок |
| Разбор | Web Worker получает `ArrayBuffer`, собирает типизированные массивы и возвращает их передачей владения (без копирования); главный поток только создаёт буферы three |
| Выбор лучом | Луч строится в float64 в мировых координатах. Грубо — three-mesh-bvh по загруженным частям (BVH строит Worker, лениво, только для частей под курсором). Точно — `POST /api/v1/pick` в ядре по исходным float64: треугольник, вершины, площадь, угол и азимут падения. Цель: ≤ 50 мс каркас, ≤ 100 мс блок |
| Потеря контекста | `webglcontextlost` → `preventDefault()`, кадры останавливаются, плашка «Графика перезапускается…»; `webglcontextrestored` → ресурсы создаются заново из данных ядра (ETag) по текущему состоянию сцены, которое хранится вне three. Без перезапуска приложения. Три потери за минуту → бюджеты вдвое меньше и сообщение |
| Нет WebGL2 | Окно диагностики (строка видеокарты, причина, совет обновить драйвер) и кнопка «Программная отрисовка (медленно)» — перезапуск с `BF_SOFTWARE_GL=1` (оболочка добавляет `--use-angle=swiftshader --enable-unsafe-swiftshader`). По умолчанию программный рендер выключен |

### 5. Как проверяем без GPU и что проверяет заказчик

| Кто | Что | Чем |
|-----|-----|-----|
| Облако, Linux CI | Точность: 200 тыс. точек на 16 км в UTM после перевода в float32 ≤ 0,5 мм | vitest (интерфейс) и pytest (выбор `origin` в ядре) |
| Облако, Linux CI | Выбор LOD, бюджет треугольников, менеджер памяти, отбор по пирамиде, перенос начала сцены | vitest в node, без WebGL |
| Облако и `windows-latest` | Кадр рисуется: демо-проект, сравнение снимка с допуском, чтение пикселей, потеря контекста через `WEBGL_lose_context`, клик по каркасу | Playwright `_electron` под программным рендером; его включает тестовый запуск явно (`BF_SOFTWARE_GL=1`), не полагаясь на Playwright. Сцены E2E ≤ 200 тыс. треугольников |
| Облако | Скорость 3D **не проверяется**: программный рендер ≈ 1 кадр/с на 1 млн треугольников | — |
| Заказчик, вехи В2+ | Кадры/с на встроенной графике | `Ctrl+Shift+F` — счётчик в приложении: кадры/с (текущее, минимум, среднее), мс на кадр, треугольников и вызовов отрисовки в кадре, оценка памяти видеокарты, класс и строка видеокарты, доля «упрощено». Дымовой сценарий: демо + каркас 10 млн + 50 тыс. стволов, вращение 10 с, итог — в журнал с кнопкой «Скопировать» |

## Причины

- Встроенная графика ограничена пропускной способностью памяти и общей с ОЗУ видеопамятью: решают число треугольников в кадре и объём буферов — отсюда части, три уровня LOD, `Uint16`-индексы, отказ от нормалей и жёсткие бюджеты.
- Отрисовка по требованию убирает постоянную нагрузку и нагрев ноутбука в простое.
- float32 от целочисленного начала — единственный способ уложиться в 0,5 мм на UTM без удвоения буферов; арифметика в п. 2 показывает запас.
- Точный выбор в ядре гарантирует, что свойства треугольника и измерения не зависят от LOD.

## Последствия

- На каждый новый вид объектов нужны: расчёт `origin`, деление на части, LOD (или обоснованный отказ) и учёт в менеджере памяти.
- Плоское затенение — сглаженных нормалей нет (для геологических каркасов приемлемо; при необходимости — настройка с пересчётом памяти).
- Числа кадров/с на вехах зависят от ПК заказчика; до В2 реальных замеров на встроенной графике у исполнителя нет — это явно указывается в отчётах.
- Кеш LOD в `cache\` увеличивает проект на ~15 % объёма каркасов.

## Альтернативы

| Вариант | Почему нет |
|---------|-----------|
| WebGPU | Исключён ТЗ 6.8 для v1; поведение на драйверах встроенной графики менее предсказуемо |
| Двойная точность на видеокарте (две float32 на координату) | Вдвое больше буферов и сложнее шейдеры; начало объекта решает задачу до 16 км |
| Непрерывный цикл кадров | Лишняя нагрузка на встроенную графику и батарею |
| Сжатие геометрии (meshopt, Draco) | Данные локальные, сеть не узкое место; распаковка тратит CPU |
| Только грубый выбор в окне (без ядра) | Результат зависел бы от LOD и float32 — нарушает 5.4 |
| Отрисовка в Worker (`OffscreenCanvas`) | Усложняет события и потерю контекста; вернуться, если главный поток станет узким местом |
| **Предложение:** на Э6 добавить в `bench/` замер времени кадра под программным рендером как индикатор регрессий (относительный, не бюджет) | Абсолютных кадров/с не даёт, но ловит рост числа вызовов отрисовки |
