## Контекст

- ТЗ 8.4: контрольные пробы (SAMPLE_ID, HOLE, TYPE, PARENT_ID, CRM_ID, LAB, BATCH, DATE, SEQ, элементы) «в таблице проб или отдельно»; справочник CRM; DL по элементу и лаборатории или полем; стандарты (z, серии, подмена, смещение), бланки, партии, дубликаты (HARD, HRD, AMPD, ранжированный HARD, рассеяние), Томпсон–Ховарт, внешний контроль; фильтры на все графики и отчёт; вкладка «QAQC»; отчёт XLSX (7 листов, графики PNG × 2) и PDF «через 8.12»; в проекте — настройка, справочник CRM, объекты «Отчёт QAQC». Цели: 1 млн контрольных записей — пересчёт после смены фильтра ≤ 3 с; графики до 100 тыс. точек — ≥ 30 кадров/с; XLSX и PDF — ≤ 60 с каждый. ТЗ 11.1 даёт Э14 2 окна.

## Варианты

| Вопрос | Варианты | Выбор и причина |
|---|---|---|
| Где хранятся контрольные пробы | А) объект «Данные QAQC» (`objects`) + неизменяемый Parquet в `blobs`; источник — файл или таблица набора (снимок); Б) таблица набора `dh_tables(kind="qaqc")` с `hole_id` NULL — миграция и правки импорта, аудита, панели «Таблица»; В) таблицы `qaqc_samples`, `qaqc_crm` — миграция 0008, `archive/spec.py`, путь PostgreSQL | **А.** 8.0.2 и 6.5: массивы — неизменяемые файлы `blobs`; CRM и бланки без скважины; 1 млн записей читается за 0,05–0,3 с; SHA-256 файла — готовый «хеш данных» отчёта; `objects` и `blob_owners` уже в `.bfggis`; миграции нет. Б и В — чтение строк SQLite (находка 4), миграция и правки чужих модулей (импорт, аудит, панель «Таблица», `archive/spec.py`) ради того же |
| Исходная проба дубликата и предыдущая проба партии | А) находятся один раз при импорте и пишутся в строку контрольной записи; Б) соединение при каждом расчёте | **А.** Строка самодостаточна: фильтр — построчная маска, пересчёт не соединяет 1 млн строк, Т8.4-8 выполняется по построению (решение 12) |
| TYPE | А) нормализовать при импорте; Б) хранить код файла, сопоставлять при расчёте по настройке проекта | **Б.** Правка соответствия («STD» → CRM) действует сразу, без повторного импорта; нераспознанные коды видны со счётчиками |
| Где считается | А) синхронно в процессе API (как графики Э13); Б) задания `jobs`; В) в интерфейсе | **А** для вкладки (цель 3 с, отклик «фильтр → график»); **Б** — импорт данных и отчёт (дольше 1 с, 8.0.2) |
| Ядра | А) numpy над сжатыми массивами; Б) numba | **А.** Замеры (находка 6) укладываются с запасом; нет первой компиляции и шага прогрева (урок Э12 на Windows-CI) |
| XLSX | А) openpyxl; Б) потоковый `Book` Э12 + картинки; В) XlsxWriter (BSD, новая зависимость) | **Б.** А не укладывается в 60 с; В — зависимость через ADR 0001 ради ≈ 150 строк разметки рисунков |
| PDF | А) отложить на Э22 (8.12), отчёт хранит всё нужное для печати; Б) минимальный путь сейчас: HTML отчёта в скрытом окне → `printToPDF` (≈ 3–4 подшага, код оболочки, прогон на .exe); В) reportlab (BSD) в ядре | **А.** ТЗ: «PDF через 8.12», 8.12 называет отчёты источником таблиц макета; Б — код, который Э22 заменит, и риск для единственной итерации Windows-CI; В — вторая система вёрстки и зависимость |
| Графики отчёта | А) PNG × 2 из интерфейса теми же компонентами, по снимку отчёта; Б) рисовать в ядре | **А** — текст ТЗ; Б — второй рисовальщик |

## Решение

### 1. Имена и состав

| Что | Решение |
|---|---|
| Ядро, расчёты (чистые функции над массивами numpy, без БД) | `core/bf_core/qaqc/`: `limits` (пороги, проверка диапазонов, допуск сравнений), `standards`, `blanks`, `batches`, `duplicates`, `thompson`, `external`, `filters` (модель фильтра → маска), `calc` (записи + настройка + CRM + фильтр + элемент → разделы) |
| Ядро, данные и API | `qaqc/records` (схема записей, Parquet, кеш колонок), `normalize` (таблица файла → записи), `source_table` (таблица набора → записи), `config` (настройка, DL, справочник CRM), `service` (объекты, версии), `jobs` (`qaqc.import`, `qaqc.report`, `qaqc.report_file`), `router` + `routes_calc`, `routes_reports`, `report` (сводка, снимок входов, хеши), `report_xlsx` (листы) |
| Интерфейс | `ui/src/modules/qaqc/` (команды `qaqc.*`, состояние, фильтры, вкладка и подвкладки, окно «Настройка», отчёты в дереве), `ui/src/charts/qaqc/` (контрольная карта, бланки, рассеяние пар, ранжированный HARD, Т-Х) |
| Данные тестов | `tools/gen/qaqc.py` — генератор контрольных записей (состав, число CRM, лабораторий, партий, зерно) для pytest, замеров и E2E; ряды Т8.4-1…7 — в самих тестах |
| Правки чужих файлов (по одному владельцу) | `composites/ore_xlsx.py`: картинки, числовые форматы, постоянная дата zip (14.11); `stats/bootstrap.py`: публичное имя `draws` у `_draws`, поведение прежнее (14.7) |
| Зависимости | Новых нет (решение 27) |

### 2. Данные QAQC: объект, записи, нормализация

| Что | Решение |
|---|---|
| Объект | `objects(kind="qaqc_data", parent_id=NULL)`, до 50 на проект; `meta` (`v: 1`): `uid`, источник (`file` — имя и SHA-256 файла; `table` — `set_id`, `name_key`, `rev`), сопоставление колонок, элементы с единицами, прочие поля, счётчики импорта, охват дат. Файл записей — blob роли `records` (Parquet zstd, группы строк по 250 тыс.). Повторный импорт заменяет blob и увеличивает `version` |
| Миграция | Нет: `db/schema.py` не меняется; `.bfggis` — через `objects`, `blob_owners`, `settings` (тест цикла, 10.5 п. 5) |
| Колонки записей | `sample_id`, `hole`, `type_code` (код файла как есть), `parent_id`, `crm_id`, `lab`, `batch` — текст (словарём, кроме id); `date` — timestamp[ms] или пусто; `seq` — float64; `parent_row`, `prev_row` — int32 (−1 — нет), `parent_lab`; на элемент E: `v:E` — значение float64 (NaN — пропуск), `q:E` — признак (0 — число, 1 — ниже DL, 2 — выше), `p:E` — значение исходной пробы, `b:E` — значение предыдущей пробы партии, `dl:E` — DL полем (если сопоставлен); прочие поля `x:<имя>` (до 40) — для фильтра «любое поле» |
| Пределы | ≤ 5 млн строк (вместе с ORIG), ≤ 60 элементов; больше — 422 с подсказкой оставить контрольные пробы и их исходные |
| Числа и даты | Числа — `formats/numbers` («<0,01» → 0,005 с `q = 1`; пропуск — NaN, не 0). Даты: ISO `ГГГГ-ММ-ДД[ чч:мм[:сс]]`, `ДД.ММ.ГГГГ[ чч:мм]`, `ДД/ММ/ГГГГ`, дата Excel; неразобранные — пусто и в счётчик |
| Исходная проба | `PARENT_ID` → первая строка с таким `SAMPLE_ID` (сравнение после обрезки пробелов, без учёта регистра); значения исходной пишутся в `p:E`, её лаборатория — в `parent_lab`; не найдена — `parent_row = −1`, счётчик `no_parent`; повторы `SAMPLE_ID` — счётчик `dup_ids`. Желательно: «широкая» раскладка — колонка исходного значения в сопоставлении заполняет `p:E` напрямую (вопрос № 36) |
| Предыдущая проба партии | В пределах (LAB, BATCH) по (SEQ, строка файла): предыдущая запись любого типа → `prev_row`, `b:E`; без партии — нет |
| Из файла | CSV, TXT, DAT, XLSX, XLS — `formats/registry.read_table`; форма сопоставления с автоподбором по именам (SAMPLE_ID, HOLE, TYPE, PARENT_ID, CRM_ID, LAB, BATCH, DATE, SEQ; остальные числовые — элементы, единица — из имени «AU_ppm», «Cu, %» или вручную) |
| Из таблицы набора | Таблица проб набора (`composites/source.read`), HOLE — имя скважины; снимок: в `meta` — `rev` таблицы, при его росте данные помечены «устарели», «Обновить» повторяет импорт с тем же сопоставлением (вопрос № 37) |
| Правка записей | Нет: данные неизменяемы, исправление — повторный импорт. Исключение проб вручную — не в Э14 (решение 23) |

### 3. Настройка проекта и справочник CRM

| Что | Решение |
|---|---|
| Где | `settings(scope="qaqc")`: ключ `config` — типы, DL, пороги; ключ `crm` — справочник. JSON `v: 1`, `version` строки — оптимистичная блокировка (`expected_version`, 409). Событие `qaqc.changed {what, version}` |
| Типы | `types`: код файла → ORIG, CRM, BLANK, DUP_F, DUP_C, DUP_P, UMP (несколько кодов на тип; сравнение без регистра и крайних пробелов). По умолчанию: сами имена типов, «STD», «STANDARD» → CRM, «BLK» → BLANK; пустой код → ORIG (`empty_is_orig`, по умолчанию да). Нераспознанный код — «не распознано»: в расчёт не идёт, считается и показан в «Настройка → Типы» с числом записей; в ORIG молча не превращается |
| DL | Таблица `dl`: (элемент, лаборатория или «любая») → значение, единица. Порядок поиска: `dl:E` записи → (элемент, лаборатория) → (элемент, любая) → нет. Нет DL: бланк «не оценён» (не «норма»), у дубликатов отсев по k_д·DL не применяется с примечанием |
| Пороги (`limits`) | `sigma_warn` 2 и `sigma_fail` 3 (1–5, warn < fail); `run` 9 (5–20); `k_blank` 5 (1–50); `k_dup` 5 (0–50); `th_group` 11 (5–51, нечётное); критерии HARD: `hard_p` 10, `hard_c` 20, `hard_f` 30, `hard_ump` 10 (% ; 1–100), `hard_share` 90 (%; 50–100); `n_boot` 1000 (100–5000), `seed` 12345. Вне диапазона — 422 `bad_param {param}`. Классы смещения 5 и 10 %, окно скользящего среднего 10, минимум 50 пар Т-Х — постоянные ТЗ |
| Справочник CRM | Строки `{crm_id, element, mean, sd, unit, source}`, ≤ 5000; ключ (CRM_ID, элемент) без регистра; `mean` > 0, `sd` > 0 — иначе строка отклоняется с номером. Загрузка из CSV / XLSX (желательно) — чтение файла в строки формы, запись — тем же `PUT` |
| Единицы | Известные: г/т = ppm, ppb = 10⁻³ ppm, % = 10⁴ ppm — пересчитываются; иное несовпадение единиц CRM или DL с единицей элемента — группа «единицы не совпадают», без оценки, с подсказкой (вопрос № 42) |

### 4. Алгоритмы 8.4.2 — чистые ядра (вход — сжатые массивы после фильтра; выход — массивы и числа)

| Раздел | Правило | Допуск, тест |
|---|---|---|
| Сравнения с порогами | `a ≤ b` считается как `a ≤ b + 1e−9·max(1, \|b\|)`, `a > b` — как его отрицание: значение ровно на границе (2σ, 3σ, k_б·DL, HARD 10 %) относится к мягкой стороне | 1,10 при μ = 1,00, σ = 0,05 — «норма» |
| Стандарты: группа и порядок | Группа — CRM × элемент × лаборатория (пустая лаборатория — своя группа). Порядок — (DATE, SEQ, строка файла), пустые дата и SEQ — в конце; пробы без значения в ряд не входят и считаются. Нет CRM в справочнике или единицы не совпадают — группа без оценки (`no_reference`, `unit_mismatch`) | Счётчики — точно |
| z и статус | z = (x − μ) / σ; \|z\| ≤ k₂ — норма (0); k₂ < \|z\| ≤ k₃ — предупреждение (1); \|z\| > k₃ — отказ (2); k₂, k₃ — `sigma_warn`, `sigma_fail` | Т8.4-1 |
| Две подряд | Проба с k₂ < \|z\| ≤ k₃, у которой предыдущая проба ряда тоже в k₂ < \|z\| ≤ k₃ и по ту же сторону μ, — отказ (правило `pair`); третья подряд — тоже отказ. Предыдущая с \|z\| > k₃ пару не образует | Т8.4-1: 1,11 — предупреждение, 1,12 — отказ |
| Серия | Длина серии — число подряд идущих проб по одну сторону μ; z = 0 серию обрывает. Проба с длиной серии ≥ `run` получает признак `bias_run` и статус не ниже «предупреждение» (9-я, 10-я, … пока серия длится) | Т8.4-1: «смещение» на 9-й пробе 1,01 |
| Подмена | \|z\| > k₃ и \|x − μ_j\| ≤ k₂·σ_j для другого CRM j того же элемента (единицы приведены) → пометка «возможна подмена: j» (до трёх ближайших по \|z_j\|); статус остаётся «отказ» | Ручной пример |
| Смещение и карта | x̄ — по всем значениям группы (вопрос № 40); смещение = 100·(x̄ − μ) / μ, %; \|…\| ≤ 5 — норма, ≤ 10 — внимание, больше — недопустимо. Скользящее среднее — по 10 последним значениям, у первых девяти пусто | 1e−12 отн. |
| Бланки | Отказ при x > k_б·DL; значение «ниже DL» (половина предела) — норма; без DL — «не оценён». Перенос загрязнения: пары (значение предыдущей пробы партии `b:E`, значение бланка), r Пирсона, n | Т8.4-2 |
| Партии | Ключ — (LAB, BATCH); отказ, если в партии есть отказ CRM (по z, паре) или бланка; `bias_run` партию не бракует. Во вкладке — по активному элементу, в отчёте — по каждому элементу и «по любому» (вопрос № 41). Записи без партии считаются отдельно | Ручной пример |
| Дубликаты | x1 = `p:E` (исходная), x2 = `v:E`; тип — DUP_F, DUP_C, DUP_P порознь. HARD = 100·\|x1 − x2\| / (x1 + x2); HRD = 100·(x1 − x2) / (x1 + x2); AMPD = 2·HARD. В расчёт — пары без NaN, с x1 + x2 > 0, без отрицательных, с m = (x1 + x2) / 2 ≥ k_д·DL (DL — лаборатории дубликата); отброшенное считается: `no_parent`, `missing`, `negative`, `zero`, `below` | Т8.4-3 (1e−12) |
| Ранжированный HARD и критерий | HARD по возрастанию против 100·i / n, i = 1…n; доли пар с HARD ≤ 10, ≤ 20, ≤ 30 % и ≤ порога типа; критерий выполнен, если доля ≥ `hard_share` при пороге типа (`hard_p`, `hard_c`, `hard_f`). В ответе — до 2000 точек (при n ≤ 2000 — все), доли — по всем парам | Т8.4-4 — точно (пары (100 + h; 100 − h), h = 1…20 дают HARD = h) |
| Рассеяние пар | Точки (x1; x2), линии 1:1, y = (1 ± 0,1)·x, y = (1 ± 0,2)·x, RMA (моменты `stats/scatter`), r Пирсона | RMA на y = x: b = 1, a = 0 точно |
| Томпсон–Ховарт | Нужно ≥ 50 пар, иначе состояние `few_pairs`. Пары по возрастанию m (устойчивая сортировка), группы по `th_group`, неполная последняя — к предыдущей; в группе — среднее m̄_g и медиана \|x1 − x2\|; МНК med_g = a + b·m̄_g; K = 1 / (√2·Φ⁻¹(0,75)) (`scipy.special.ndtri`); σ(c) = K·(a + b·c); P(c) = 200·σ(c) / c, % — для P10, P50, P90 значений m и заданных c; a + b·c ≤ 0 — пусто | Т8.4-5: a = 0, b = 0,1 (1e−12), P = 20,9672 % (1e−4); Т8.4-6: K·b ∈ [0,045; 0,055], зёрна 0–9 |
| Данные Т8.4-6 | `rng = Generator(PCG64(seed))`; t = `rng.uniform(1, 10, 11000)`; x1 = t·(1 + 0,05·`rng.standard_normal(11000)`); x2 — так же вторым вызовом | Проверено проектом: 0,0483…0,0541 |
| Внешний контроль | Тип UMP; группа — элемент × (лаборатория исходной `parent_lab`, лаборатория контроля). x1 — основная, x2 — контрольная; отбор и метрики — как у дубликатов (критерий `hard_ump`); смещение = 100·(x̄₁ − x̄₂) / x̄₂; парный t-критерий `scipy.stats.ttest_rel(x1, x2)`: t, p, число степеней свободы; все разности равны — t и p пусты с примечанием (не NaN в ответе); RMA y = a + b·x (x — основная): наклон, свободный член | Т8.4-7: смещение 0, b = 1, a = 0 точно |
| Интервалы RMA | Бутстрап пар с возвратом, выборки — `stats/bootstrap.draws` (PCG64 по зерну, одно зерно на каждую группу); по реализации — суммы пяти моментов; интервал — процентили 2,5 и 97,5 (линейная интерполяция). Реализаций B = `n_boot`, но n·B ≤ 10⁸: при большем n — B = ⌊10⁸ / n⌋, не меньше 100; число реализаций — в ответе и отчёте (вопрос № 39) | Одно зерно — один результат; на равных значениях интервалы [1; 1] и [0; 0] |

### 5. Фильтры и порядок расчёта

| Что | Решение |
|---|---|
| Модель фильтра | JSON `v: 1`: `labs[]`, `batches[]`, `date_from`, `date_to`, `crm[]`, `types[]` (типы после сопоставления), `hole_prefix`, `where[]` — до 20 условий «любое поле» `{field, op, value}` (текст: `eq`, `ne`, `in`, `prefix`, `contains`, `empty`; число и дата: `eq`, `ge`, `le`, `between`, `empty`); условия соединяются «И». Элемент — не фильтр строк, а выбор колонок: во вкладке — активный элемент, в отчёте — список |
| Действие | Фильтр — построчная маска по полям самой записи; один и тот же фильтр — у всех подвкладок, графиков и отчёта; в отчёте сохраняется целиком |
| Порядок расчёта | 1) сопоставление типов по словарю кодов; 2) маска фильтра; 3) сжатие колонок в исходном порядке строк; 4) ядра получают только сжатые массивы; 5) группы выводятся по названиям (CRM, лаборатория, партия), не по внутренним кодам; суммы — numpy по сжатым массивам |
| Следствие (Т8.4-8) | Расчёт по фильтру и расчёт по заранее отобранному подмножеству записей (`records.take(mask)`, порядок сохранён) получают одинаковые массивы в одинаковом порядке — результат побитно равен по построению. Серии стандартов считаются по отфильтрованному ряду в обоих случаях |
| Что сравнивается в Т8.4-8 | Канонический JSON сводки отчёта (ключи по алфавиту, числа — `repr`) и XML листов «Сводка» … «Партии» в XLSX — побайтно; лист «Параметры» не сравнивается (в нём фильтр, хеши, время) |

### 6. Где считается, кеш, задания

### 7. Объект «Отчёт QAQC»

| Что | Решение |
|---|---|
| Объект | `objects(kind="qaqc_report", parent_id=NULL)`, раздел дерева «Отчёты», ≤ 200 на проект. От объекта данных не зависит: `meta` хранит `data_uid`, имя данных и SHA-256 записей; ссылок `object_refs` и перенумерации id при импорте `.bfggis` нет |
| Файлы (`blob_owners`, владелец — отчёт) | `records` — тот же файл записей, что был у данных (общий blob: отчёт воспроизводим и после замены или удаления данных); `inputs` — JSON: настройка, справочник CRM, фильтр, элементы, параметры, зерно, `algo: "qaqc-1"`, версии numpy / scipy / pyarrow, время; `summary` — JSON результатов по группам (без построчных таблиц); `img/<ключ>` — PNG графиков; `xlsx` (позже `pdf`) |
| Хеши | `data_sha256` — SHA-256 файла записей; `inputs_sha256` — SHA-256 канонического `inputs` вместе с `data_sha256`; оба — в `meta`, на листе «Параметры» и в окне отчёта |
| «Устарел» | Вычисляется при чтении: у данных с тем же `uid` другой SHA-256 записей (`data`), изменились настройка или справочник (`config`), данные удалены (`source_deleted`). «Перестроить» повторяет расчёт с сохранёнными фильтром и параметрами на текущих данных и настройке (версия объекта + 1; при `source_deleted` — недоступно с причиной) |
| Построчные таблицы | В объекте не хранятся: `qaqc.report_file` считает их заново теми же ядрами по `records` и `inputs` отчёта |
| Графики | Интерфейс рисует теми же компонентами, что и вкладка, запрашивая расчёт по `report_id` (снимок отчёта, не текущие данные), и передаёт PNG × 2. Состав: контрольная карта каждой группы стандартов, бланки по лабораториям, на каждый тип дубликатов — рассеяние, ранжированный HARD, Т-Х, рассеяние групп внешнего контроля; режим `charts: all / flagged / none` (`flagged` — группы с предупреждениями и отказами и сводные графики), не больше 200, сверх — строка в «Сводке» |
| Размер | Отчёт удерживает копию записей (34 МБ на 1 млн) и картинки (≤ 200 × ≈ 150 КБ); удаление отчёта освобождает их обычной сборкой `storage/gc` |

Правила: 15 команд объявляются одним подшагом (14.15) с параметрами и заглушками. Кнопки ленты — список `QAQC_BUTTONS` из `modules/qaqc/commands.ts`: «Настройка» и шесть разделов (`qaqc.open {section}`). Недоступность — с причиной: «Откройте проект», «Загрузите контрольные пробы: „Анализ → QAQC → Настройка“», «PDF появится на этапе Э22». Признак confirm (вызов ассистента — после подтверждения пользователя) — у всего, что меняет сохранённое и влияет на готовые результаты: настройка и справочник CRM (отчёты становятся «устаревшими»), замена и обновление данных, удаление. Новые данные, новый отчёт, фильтр, открытие разделов, сохранение файла — без confirm (пробы наборов не меняются, ничего не теряется). Ассистенту команда возвращает короткий текст: `qaqc.open` — число записей и долю отказов раздела; `qaqc.report` — имя и id отчёта, число партий и отказов, критерии дубликатов.

## Последствия

- Новое: пакет `bf_core/qaqc` (≈ 20 модулей), API `/qaqc`, виды объектов `qaqc_data` и `qaqc_report`, область `settings` `qaqc`, задания `qaqc.import`, `qaqc.report`, `qaqc.report_file`, модуль интерфейса `modules/qaqc`, графики `charts/qaqc`, вкладка нижней панели «QAQC», раздел дерева «Отчёты», группа ленты «Анализ → QAQC» (15 команд).
- Схема БД не меняется, миграций нет; `.bfggis` прежних версий читается без изменений; lock-файлы не меняются.
- `composites/ore_xlsx.Book` получает рисунки и числовые форматы; ими смогут пользоваться отчёты следующих этапов (пересечения Э15, ресурсы Э20, «Таблица в XLSX» Э22) — решения остаются за их ADR.
- Э22 (8.12): печать отчёта QAQC макетом (PDF) из `summary` и графиков по `report_id`; раздел «Отчёты» принимает отчёты следующих этапов; Э23: команды `qaqc.*` для ассистента.
- В ТЗ (docx): ответы № 35–43 — в 7.35 новым подпунктом после ответа владельца; при ответе «PDF сейчас» на № 35 — отдельная доработка после Э14.
