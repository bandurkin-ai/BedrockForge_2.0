# ADR 0002. Процессы и хранение данных

**Статус:** Принято, 2026-11-16 (Э0). Подтверждается спайками в, г и тестами Э1–Э2.

## Контекст

- ТЗ 6.1–6.2, 6.4–6.7, 5.5, 5.6 (S1, S2), 7.3, 7.6, 17.2, 17.3. Очередь BF (PostgreSQL `SKIP LOCKED`) и advisory lock хранилища не переносятся (Приложение Е).
- Проверено в облаке (Linux, Electron 45.2.3 / Chromium 156): страница `app://bedrockforge` обращается к `http://127.0.0.1:<порт>` — 401 без токена, 200 с `X-BF-Token`, `Range` → 206 с читаемым `ETag`, SSE через `fetch`; запросов разрешения Local Network Access нет. Захват задания одним `UPDATE … RETURNING` работает на SQLite 3.53.1 (Python 3.12.16).

## Решение

### 1. Процессы

| Процесс | Кто запускает | Роль | Не делает |
|---------|---------------|------|-----------|
| `BedrockForge.exe` (main) | Пользователь | Окно, заставка, `app://`, запуск и контроль ядра, лицензия, обновление, `safeStorage` | Расчёты, доступ к БД |
| Окно (renderer) + Web Workers | main | Интерфейс, 3D; `contextIsolation`, `sandbox`, без `nodeIntegration` | Доступ к файлам и ОС (только preload) |
| `bf-core.exe` (ядро) | main | API, БД, планировщик заданий, SSE, сборщик blobs, автокопии | Отрисовку |
| Исполнители: `heavy` × N, `quick` × 1 | ядро (`spawn`) | Обработчики заданий, свой engine БД | Доступ к UI |

### 2. Жизненный цикл ядра

| Шаг | Решение |
|-----|---------|
| Старт | `bf-core.exe --port 0 --token <32 байта hex> --data <корень данных> --parent-pid <pid>`; `windowsHide`; вывод UTF-8 |
| Готовность | Ядро само открывает сокет `127.0.0.1:0` и передаёт его uvicorn (нет гонки за порт), печатает одну строку `BF-READY port=<n> version=<v>`; main ждёт ≤ 30 с, затем `GET /api/v1/health` и требует равенства версии сборки |
| Быстрый старт | До `BF-READY` импортируются только fastapi, SQLAlchemy, pydantic (в облаке 0,4 с); numpy, pandas, numba, pyarrow, duckdb — лениво и в исполнителях (ещё 1–5 с); тест бюджета импорта |
| Сбой | Выход процесса или 3 пропуска `health` подряд → перезапуск, не больше 3 за 5 мин (скользящее окно), сообщение «Вычислительное ядро перезапущено»; затем окно «Ядро не запускается» с журналом |
| Завершение | `POST /api/v1/shutdown` (стоп приёма, отмена заданий, checkpoint WAL) → ожидание 10 с → `taskkill /PID <ядро> /T /F` |
| Дерево процессов | Ядро при старте создаёт Job Object `KILL_ON_JOB_CLOSE` (ctypes) и входит в него; исполнители — во вложенных Job Object (лимит памяти). Ядро следит за `--parent-pid` и EOF stdin: оболочка исчезла → штатный выход. Нативных модулей Node не требуется |
| Один экземпляр | `app.requestSingleInstanceLock()`; `second-instance` активирует окно и передаёт путь `.bfggis` / `project.bfproj` |

### 3. Доступ к API (S1, S2)

| Правило | Значение |
|---------|----------|
| Сеть | Только `127.0.0.1`, случайный порт; HTTP/1.1, префикс `/api/v1` |
| Токен | `X-BF-Token` на каждом запросе (кроме CORS-preflight `OPTIONS`), сравнение за постоянное время; нет или неверный → 401. В URL токен не передаётся |
| `Host` | Строго `127.0.0.1:<порт>`, иначе 403 (защита от DNS rebinding) |
| `Origin` | `app://bedrockforge` или отсутствует (main, тесты); иной → 403. CORS: `Allow-Origin: app://bedrockforge`; заголовки `X-BF-Token, Range, If-None-Match, Content-Type`; `Expose: ETag, Content-Range, Accept-Ranges`; `Max-Age: 7200` |
| Окно | Адрес и токен получает через preload; CSP `connect-src http://127.0.0.1:*` |
| События | `GET /api/v1/events` (SSE) читается через `fetch` + поток (`EventSource` не умеет заголовки); `id` и `Last-Event-ID`, пульс 15 с, одно соединение на окно; загрузок массивов одновременно ≤ 4 (предел 6 соединений на хост) |

### 4. Задания

| Тема | Решение |
|------|---------|
| Хранение | `jobs` и `job_log` (построчный журнал) в `project.sqlite`; задания без проекта (`import.project`, демо, удаление проекта) — те же таблицы в `instance.sqlite` профиля |
| Очереди | `heavy`: N = min(ядра − 1, ОЗУ / 3 ГБ), не меньше 1 (настройка); `quick`: один постоянно работающий «тёплый» исполнитель — не ждёт тяжёлых |
| Захват | Только планировщик в ядре, транзакция `BEGIN IMMEDIATE`: `UPDATE jobs SET status='running', attempts=attempts+1, started_at=…, worker=… WHERE id=(SELECT id FROM jobs WHERE status='queued' AND queue=:q ORDER BY priority, id LIMIT 1) RETURNING …`. В SQLite писатель один — оператор атомарен без `SKIP LOCKED`; для PostgreSQL тот же `dialect.claim_job()` добавляет `FOR UPDATE SKIP LOCKED`. Секрет задания (пароль архива) читается и обнуляется в этой же транзакции |
| Исполнители | `multiprocessing.get_context("spawn")`, вход `bf_core.jobs.worker:main`, обработчики — явным импортом `bf_core.jobs.registry`; `freeze_support()` первой строкой; тест с настоящими процессами. `heavy` перезапускается после `MemoryError` и при росте RSS выше порога |
| Прогресс | Обработчик вызывает `tick(progress, message)` не реже 1 раза в секунду → канал → планировщик → SSE; в БД прогресс не чаще 1 раза в секунду, `heartbeat_at` — раз в 5 с |
| Отмена | `queued` → сразу `cancelled`; `running` → `cancel_requested` и сообщение в канал, `tick()` бросает `JobCancelled`; нет реакции 15 с → процесс снимается |
| Частичный результат | Задание пишет порциями (короткие транзакции ≤ 50 тыс. строк) в объекты с `state='building'`, невидимые интерфейсу; последняя транзакция ставит `ready` и регистрирует blobs. Отмена, сбой, старт ядра → удаление `building`. Долгих транзакций записи нет — `quick` и правки таблиц не блокируются |
| Память | Обработчик объявляет `estimate_memory(params)`; старт, если оценка ≤ свободная ОЗУ − 1,5 ГБ, иначе ждёт с причиной «Недостаточно памяти…»; оценка > всей ОЗУ → ошибка сразу. Лимит `JOB_OBJECT_LIMIT_PROCESS_MEMORY` на исполнителя; превышение → «Не хватило памяти: нужно ~N ГБ, доступно M ГБ…», очередь продолжает |
| После перезапуска | `running` → `queued`, если `attempts < max_attempts`, иначе «Ошибка»; `attempts` растёт при каждом захвате; `max_attempts` = 3, для `import.*` — 2 |
| Потоки | Потоки numba и BLAS на исполнителя = ядра / N (`threadpoolctl`) — нет переподписки, воспроизводимые результаты |

### 5. Папка проекта `<Имя>.bfproj\`

| Путь | Содержимое и правила |
|------|----------------------|
| `project.bfproj` | Манифест JSON (uid, название, версия формата): файл для двойного щелчка — папку Проводник как документ не открывает |
| `project.sqlite` | WAL, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=30000`; запись только через ядро и его исполнителей, транзакции записи — `BEGIN IMMEDIATE`; при закрытии `wal_checkpoint(TRUNCATE)` |
| `blobs\ab\cd\<sha256>`, `blobs\.tmp\` | Неизменяемые файлы; имя — SHA-256 содержимого |
| `cache\` | Производные данные (LOD, тайлы, колоночные снимки таблиц); удаляется без потерь |
| `backups\` | `VACUUM INTO` во временный файл и переименование; раз в сутки (при открытии, если прошло > 24 ч, и по таймеру), 5 последних; перед миграцией схемы — отдельная копия |
| `logs\` | Журналы исполнителей проекта |
| `project.lock` | Ядро держит файл открытым с `LockFileEx` всю работу с проектом (после сбоя ОС снимает блокировку сама); внутри — pid, ПК, пользователь, время. Занят → открытие «только чтение» (`mode=ro`), изменяющие запросы → 423 |

Дополнительные правила:

- **Blobs, запись:** поток во временный файл `blobs\.tmp\<uuid>` с подсчётом SHA-256 → `fsync` → в транзакции владельца (`BEGIN IMMEDIATE`): перенос на место, если файла нет (иначе временный удаляется) → строка `blobs` → строка `blob_owners` → `COMMIT`. Исходный файл импорта копируется в blobs последним шагом задания.
- **Blobs, сборщик:** каждые 30 мин и по команде, в транзакции записи (взаимное исключение с записью без advisory lock): blobs без владельцев — файл и строка удаляются; файлы без строки старше 15 мин и `.tmp` старше 24 ч — удаляются. Занятый файл (`WinError 32`, открытый `mmap`) — повтор в следующий проход. Новый тип с файлами обязан зарегистрировать вид владельца — иначе тест падает.
- **Проверка целостности:** `PRAGMA quick_check` при открытии (база < 200 МБ — сразу; больше — фоном, чтобы уложиться в 5 с до первого кадра); ошибка → предложение восстановить из копии, повреждённый файл сохраняется рядом.
- **Диски:** только локальные; сетевой путь (UNC, подключённый диск) отклоняется с объяснением (WAL требует общей памяти); длина пути проекта ≤ 180 символов.
- **Смена проекта:** проект с работающими заданиями остаётся подключённым (блокировка удерживается), пока они не завершатся.
- **Список проектов:** обход папки проектов (`*.bfproj\project.bfproj`) и чтение `project_meta`; уникальность названия — по нормализованному ключу (ADR 0003) и имени папки.

### 6. Профиль пользователя

| Путь | Содержимое |
|------|-----------|
| `%APPDATA%\BedrockForge\settings.json` | Настройки интерфейса; пишет main атомарно (временный файл + переименование), версия формата внутри |
| `%APPDATA%\BedrockForge\license\` | Лицензия, отметки пробного периода (ADR 0005) |
| `%LOCALAPPDATA%\BedrockForge\cache\` | `numba\<версия ядра>\`, временные файлы |
| `%LOCALAPPDATA%\BedrockForge\logs\` | Оболочка, ядро; ротация 10 × 10 МБ |
| `%LOCALAPPDATA%\BedrockForge\state\instance.sqlite` | **Добавлено к ТЗ 6.5:** задания без проекта и кеш списка проектов; удаляется без потери данных проектов |
| Переносимый режим | Файл-флаг `BedrockForge.portable` → всё перечисленное в `<папка exe>\data\` |

## Причины

- Единственный планировщик-захватчик исключает гонки писателей SQLite и даёт одно место для SSE, оценки памяти и объяснения «почему ждёт».
- Состояние `building` + короткие транзакции одновременно выполняют «отменённое задание не оставляет частичного результата» и «быстрые операции не ждут импорта».
- Job Object в самом ядре и слежение за родителем закрывают «висящие `bf-core.exe`» (17.2.9) без нативных модулей в оболочке.
- Блокировка файла средствами ОС не оставляет «мёртвых» `project.lock` после сбоя.

## Последствия

- Прямой доступ окна к ядру требует CORS и передачи токена в окно; XSS в окне = доступ к API (смягчается CSP и S9).
- Обработчик обязан уметь писать в `building` и вызывать `tick()`; проверяется общим тестом на каждый вид задания.
- `instance.sqlite` — второй экземпляр схемы заданий; миграции — общим набором Alembic (ADR 0003).
- Проекты на сетевых дисках не поддерживаются до Э25 (сервер ЛВС).

## Альтернативы

| Вариант | Почему нет |
|---------|-----------|
| Проксировать API через `app://` в main (как в BF) | Лишнее копирование массивов в сотни МБ через main; **запасной вариант**, если спайк в на Windows выявит блокировку обращений к 127.0.0.1 |
| Исполнители сами захватывают задания (как в BF) | Несколько пишущих процессов SQLite ради захвата; сложнее объяснять ожидание |
| Одна транзакция на весь импорт | Блокирует всех писателей до 90 с |
| Потоки вместо процессов | GIL, нет изоляции памяти и снятия зависшего задания |
| Job Object из main (нативный модуль) | Сборка нативного кода под Electron, новый риск упаковки |
| **Предложение:** передавать токен через переменную окружения, а не `--token` | Аргументы видны процессам того же пользователя; по ТЗ 6.4 оставлен `--token`, ядро принимает и `BF_TOKEN` |

## Проверка

| Что | Чем |
|-----|-----|
| **Спайк в** (`windows-latest`): `bf-core.exe` на 127.0.0.1, `BF-READY`, 401 без токена, 403 при чужом `Host`/`Origin`; из окна `app://` — `fetch`, `Range`, SSE без запросов разрешений | Скрипт спайка + Playwright |
| **Спайк г**: запуск и данные в пути с кириллицей и пробелами | ADR 0005 |
| Захват, отмена, `tick`, возврат `running` → `queued`, 3 попытки | pytest с настоящими процессами `spawn`, SQLite и PostgreSQL |
| Снятие ядра после правки не теряет правку; снятие оболочки не оставляет процессов | E2E на Windows |
| Blobs: гонка «запись — сборщик», файл без строки, занятый файл; владелец не зарегистрирован → тест падает | pytest |
| Автокопия, `quick_check`, восстановление; `project.lock` и режим «только чтение» | pytest (`-m windows`) |
| Массив: `ETag`, `Range` → 206; бюджет импорта модулей до `BF-READY` | pytest + httpx; `bench/` |
